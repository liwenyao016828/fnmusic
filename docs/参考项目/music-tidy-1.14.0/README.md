# 参考项目：music-tidy v1.14.0

> 来源：用户提供的 `music-tidy-1.14.0.fpk`（2026-09-18 解包）
> 同目录的 `../music-tidy/` 是**旧版 v1.12.0**，留着做版本对比用。

## 这是什么

一个飞牛 NAS 上的「音乐整理」应用（Python 后端 + 原生 JS 前端）。
本项目（音枢 AI）的 `pkg/ai` 就是移植自它的 `ai_llm.py`，
本项目「整理去重 / 补全歌词封面」的功能设计也大量参考它。

## 看 AI 部分从这里入手

| 文件 | 看什么 |
|---|---|
| `server/ai_llm.py`（675 行，8 个 AI 方法） | **AI 能力的全貌**。重点看 `judge_name` / `analyze_name_rule` / `_with_user` / `_sanitize_lrc` |
| `server/tidy_engine.py` | 11 个 AI 调用点。重点看 `_llm_should_rescue`（**什么时候才叫 AI**）和 `_llm_rescue`（**防幻觉约束**） |
| `server/web/app.js` | 看 AI 结果怎么透出给用户（搜 `lyric_source`、`rlm-warn`） |

**完整分析见 `../../../docs/AI 能力评估.md` §2** —— 那里逐条对比了「它做了什么 / 我建议怎么改」。

## 三件最值得抄的（已写进评估文档）

1. **「结果必须来自输入」的防幻觉约束** —— `judge_name` 要求
   「歌手与歌名都只能是文件名里出现过的文字，绝对不许换成另一首歌」，
   `_llm_rescue` 拿到结果后再校验一次，不通过就丢弃、沿用规则结果。

2. **「让 AI 生成规则」而不是「让 AI 做判断」** —— `analyze_name_rule`：
   用户给一个样例 + 一句解释 → AI 产出正则 → **校验 + 用户可手改** → 之后整库走正则。
   成本从「每首歌一次调用」降到「每种命名习惯一次」，且产出物可检查。

3. **触发条件用「规则自认可疑」而不是「字段为空」** —— `_llm_should_rescue` 里的
   `suspect` 分支（v1.13.0 才补的）。旧版只在字段为空时调 AI，
   像「好听的歌曲推荐-下山 - 麦小兜」这种**两头都错但两头都非空**的解析永远进不了兜底。

## ⚠️ 有一样不建议跟

**AI 生成歌词**（`generate_lyric`）。它的 prompt 明确写着
「若不确定完整歌词，请……创作合理、连贯……的中文歌词」—— 是**编造**。
而且时间码是估算的、不会同步。理由详见 `../../../docs/AI 能力评估.md` §5。

## 版本差异（v1.12.0 → v1.14.0）

`ai_llm.py` 的 diff 显示新增了：
- `judge_name`（候选消歧，替代原先的 `recognize` 单打独斗）
- `recognize` 的 prompt 加了两条防幻觉规则（「只能取自文件名本身」「歌单名要剔掉」）

即：**新版把「让 AI 自由发挥」改成了「让 AI 在候选里挑」**，方向和我们一致。
