# 音乐刮削 / 整理 / 元数据链路 现状报告

对象：`music-v2`（曲率，原 fn-lx-player）v2.1.30 后端
范围：`backend/pkg/{nameparse,search,match,tidy,complete,tags,ai,library,monitor}` 及相关 API 层
用途：与 Python 参考项目做能力对比，判断「哪些环节值得替换」

> 阅读约定：所有引用为 `文件:行号`，只摘关键一两行代码。

---

## 0. 一句话结论

链路的**骨架完整**（解析 → 搜索 → 匹配 → 取歌词封面 → 写标签 → 通知 NAS 重扫），
但**没有任何上游限速、缓存、重试、负缓存**；匹配只靠「归一化后曲名完全相等 + 歌手双向包含」一条硬判据，
而已经写好的 `pkg/match`（版本标记过滤 / 时长校验 / 相似度打分 / 正式版优先）**只服务于 monitor 与 push，完全没接进刮削链路**。
这是最值得对照参考项目替换的地方。

## 2. 文件名解析（`pkg/nameparse`）

### 2.1 结构

- 入口 `Parse(name string) Result`（`nameparse/nameparse.go:89`）——**永不失败**：拆不出来时 `Title` 为整串、`Artist` 为空。
- 用户规则优先层 `(*Store).Parse`（`nameparse/rules.go:192`）：先试用户正则，没命中回落内置启发式。
- `Result`（`nameparse.go:39-50`）：`Title/Artist/Album/Track/Suspect/Reason/Candidates`。
  `Candidates` 保留多种解释（`split:`/`swapped`/`drop-prefix:`/`whole`/`rule`）。
- 降级判据 `NeedsAI()`（`nameparse.go:56-60`）：`Title=="" || Artist=="" || Suspect`。

### 2.2 规则清单

| 环节 | 实现 | 说明 |
|---|---|---|
| 取 basename + 去扩展名 | `nameparse.go:92-93` | |
| 开头曲目号 | `trackNoRe = ^\s*(\d{1,3})[\s.\-_、]+` `nameparse.go:78` | `01.` / `01 ` / `01-` / `01_` / `1、`；注释承认「7 天」会被误吃 |
| 剥括号 | `bracketRe = [\(（\[【][^\)）\]】]*[\)）\]】]` `nameparse.go:81` | **括号内容被整段删除且不保留**（`(Live)`/`(Remix)`/`feat.` 全丢） |
| 分隔符 | `separators = {" - "," – "," — ","_-_"," -","- ","–","—","_"}` `nameparse.go:84` | `splitOnce` `:184` 按**最左出现**切一刀 |
| 歌手/歌名方向 | 默认左歌手右歌名 `nameparse.go:128` | 两个候选都进 `Candidates` |
| 噪声词纠正 | `noiseWords` `nameparse.go:67-72` + `matchNoise` `:218` | 歌手位命中噪声词 → 丢掉左半、拿右半再切一刀（`:136-144`） |
| 中英混排歧义 | `directionAmbiguous` `nameparse.go:241` | `isASCIIOnly(left) != isASCIIOnly(right)` → `Suspect` |
| 三段以上 | `nameparse.go:173-178` | `" - "` 计数 ≥3 → `Suspect`「超过两段」 |
| 无分隔符 | `nameparse.go:157-169` | 命中噪声词 → `Suspect`；或 `len(runes)>30` → `Suspect` |
| 开头括号 | `nameparse.go:109-115` | `【...】`/`(...)` 开头 → `Suspect`「可能是歌单前缀」 |

### 2.3 直接回答几个问题

- **多歌手 / feat. / ft.**：**没有处理**。`nameparse` 不做歌手切分，也不识别 `feat.`。
  全仓唯一的歌手切分正则 `artistSplitRe`（`match/match.go:131`，`&＆,，/、;； | vs | feat | ft`）
  只用于**相似度比较时的 `NormArtist`/`PrimaryArtist`**（`match.go:143-156`），不参与文件名解析。
- **括号版本标记**：被 `bracketRe` 删除，**不保留、不落字段**（`Result` 没有 version 字段）。
  版本判定的能力存在（`match.variantPattern` `match/match.go:27-41`），但刮削链路没调用它。
- **音质水印**：只在噪声词表里出现（`flac/ape/wav/320k/192k/128k/hq/sq/ogg`，`nameparse.go:71`），
  仅用于判定「歌手位是噪声」；**不解析成质量字段**，也不影响搜索词。
- **音轨号**：`trackNoRe` 抽到 `Result.Track`（去前导零，`nameparse.go:101-104`）；
  但注意它只用于展示，最终写标签的 `Track` 来自搜索结果（`complete.go:436-438`）。

### 2.4 用户规则层（可对照参考项目的亮点）

- `Rule` / `AllowedFields = {artist,title,album,track}`（`rules.go:33-54`）。
- `ValidateRule`（`rules.go:249-317`）**五道硬门槛**：能编译 / 组名在白名单 / 至少含 artist 或 title /
  能匹配样例 / **提取出的值必须出现在样例里**（防幻觉，`:296-300`）。
- AI 生成入口 `SuggestNameRegex`（`ai/ai.go:561`）+ `POST /api/library/name-rules`（`api/name_rules.go:28`）：
  AI 出的正则**必须先回测通过才返回给用户看，且不自动保存**（`api/name_rules.go:58-94`）。
- `Store` 落盘 `name_rules.json`（`api/server.go:133`），坏规则跳过不影响整体（`rules.go:96-109`）。

### 2.5 降级顺序（`complete.resolveName`，`complete/complete.go:854-902`）

```
索引里的 Title/Artist  →  AI JudgeName（仅当 NeedsAI 且开了 UseAINameJudge）  →  nameparse（用户规则 → 内置）
```
- `looksLikeFilename`（`complete.go:838-852`）+ `filenameExts`（`complete.go:824-827`）：
  「标题其实是文件名」时当无标题处理。
- AI 结果必须过 `nameAppearsIn` 防幻觉校验（`ai/ai.go:511-513`），否则弃用。
- 注意：**`dedupe.go` 不走 nameparse**——自己用 `strings.SplitN(base, " - ", 2)`（`tidy/dedupe.go:122-127`）。

`HandleSearch`（`aggregator.go:324-415`）：`platform=all` 时 **4 个 goroutine 并发**各取 16 条后合并（`:380-397`）。

### 3.2 搜索词构造

- 补全：`keyword = title`，有歌手则 `title + " " + artist`（`complete/complete.go:350-353`）。
- 音质查询：`name + " " + singer`，1 页 40 条（`search/qualities.go:181-236`）。
- 封面候选：`search.Search(name, artist, ...)` 每平台 10 条（`api/features.go:154-240`）。
- 每次补全每首最多 4 个平台 × 1 页 10 条（`complete.go:386`），**无二次翻页、无失败重搜**。

### 3.3 打分算法（三套并存，互不共用）

**① 搜索结果排序 `filterAndRankSongs`（`search/aggregator.go:142-290`）** —— 只用于「把平台返回排个序」：

| 条件 | 分值 |
|---|---|
| 多 token：曲名完全等 / 包含 | +3000 / +1500 |
| 多 token：歌手包含 | +3000 |
| 多 token：曲名 + 歌手双命中 | 额外 +6000 |
| 多 token：只中歌手不中曲名 | −4000 |
| 单 token：曲名完全等 / 去括号后等 / 前缀 / 包含 / 都不中 | +3000 / +2400 / +1000 / +400 / −2000 |
| 单 token：歌手完全等 | +2500 |
| 平台权威位次（kg/tx：idx%16 为 0/1/2） | +1000 / +700 / +450 |
| 平台位次（wy/kw 首位） | +400 |
| 跨平台共识（同「去括号小写曲名+歌手」，c≥2） | +1500×c |
| 专辑同名 / 无括号专辑 | +600 / +400 |
| 时长 170–340s / <120s | +250 / −500 |
| 音质 FLAC | +150 |
| 收尾 | 排序后若 `len(clean)>=6` 丢弃噪声项，否则把噪声项追加回末尾（`:286-289`） |

**② 硬匹配 `MatchByNameSinger`（`search/qualities.go:117-144`）** —— 刮削链路**实际使用的判据**：
```go
// qualities.go:123-144
if normalizeForMatch(s.Name) != normalizeForMatch(name) { return false }   // 曲名归一后必须完全相等
if singer != "" && s.Singer != "" && !contains(s.Singer, singer) && !contains(singer, s.Singer) { return false }
```
`normalizeForMatch`（`qualities.go:53-80`）：小写、去成对括号及内容、去空白与 `- _ · ・ . ，, 、 & /`。
**不含时长校验、不含版本判定、不含相似度**。

**③ 相似度 `match.Similarity`（`match/match.go:180-213`）** —— 曲名 **0.7** + 歌手 **0.3**，
`ratio = 2*LCS/(len(a)+len(b))`；阈值 `MatchMinScore=0.72`（`match.go:18`）、`StrongMatchScore=0.85`（`match.go:21`）。
**只在 `push/push.go:254-262` 与 `monitor/pipeline.go:98`（`RejectReason`）使用**。

### 3.4 噪声过滤

`isNoisySearchItem`（`aggregator.go:88-135`）：时长 >600s 或 <50s（关键词不含「铃声/片段」）即噪声；
三张词表：`noiseKeywords`（`:98-103`，伴奏/ktv/cover/翻唱/片段/铃声/剪辑/纯音乐/喊麦/慢摇/串烧/变速/降调/升调/dj/remix/男声版/女声版/抖音…）、
`singerNoise`（`:112-114`，电台/故事会/解说/有声…）、`albumNoise`（`:121-127`，翻唱/轻音乐/助眠/广播剧/有声书/评书/相声/短剧…）。

### 3.5 有没有「用搜索结果反推校验文件名」？

**没有。** 现状是单向的：
- 正向：用文件名解析出的 `title`/`artist` 做关键词 → 要求平台标题归一后**完全相等**（`qualities.go:123`）。
- 反推：不存在「拿命中的平台曲目回头校验文件名/歌手是否一致」这一步；
  唯一的防幻觉是 AI 路径上的 `nameAppearsIn`（`ai/ai.go:511`，只校验 AI 输出出自输入）与
  `ValidateRule` 的「提取值必须在样例里」（`rules.go:296-300`）。
- 副作用：平台标题带后缀（`晴天 (Live)`、`晴天（R&B版）`）时 `MatchByNameSinger` 直接不命中，
  只能落到 AI 挑候选（`complete.go:409-414`），而 AI 兜底在 API 层默认开启（`api/library_complete.go:397-431`）。

## 4. 缓存与限速

### 4.1 上游请求

- **全包只有一个客户端**：`var httpClient = &http.Client{Timeout: 8 * time.Second}`（`search/aggregator.go:84-86`）。
- 每个请求只设 `User-Agent` 与 `Referer`（`aggregator.go:505-507/533-535/591-592/657-658/737-738/821-822/904-906/974-976`；`album_qq.go:79-80`）。
- **无 `time.Sleep`、无 token bucket / 全局限速、无并发上限、无重试退避、无失败熔断**（grep 全仓确认）。
  唯一的「礼貌性」是 `complete.Options.Concurrency` 默认 2，注释写明是为「降低被平台风控的概率」（`complete.go:71-72`）。

### 4.2 缓存

| 缓存 | 位置 | TTL | 上限 | 溢出策略 |
|---|---|---|---|---|
| QQ 专辑元数据 | `albumMetaCache` `search/album_qq.go:33-66` | **无** | 1024 | **整体清空**（`:62-64`） |
| 榜单 | `charts/charts.go:141` | 15 min | — | — |
| NAS 目录扫描 | `nas/scancache.go:21-25` | 72 h | 30 目录 / 单目录 5000 首 / 32MB | LRU-ish 按时间删 |
| fnos 根目录 | `nas/pathguard.go:61-80` | 30 s | — | — |
| **搜索结果** | — | — | — | **无缓存** |
| **歌词 / 封面下载** | — | — | — | **无缓存** |
| **AI 调用结果** | — | — | — | **无缓存**（`ai/ai.go` 无 prompt 缓存） |

### 4.3 负缓存

**没有。** 搜不到 / 匹配不上的曲目没有任何「已尝试」标记：
`complete.Resolve` 每次都会全平台重搜；`enrichIndexTags` 读标签失败只 `MarkTagRead`（`api/features.go:362-397`），
下次不会重试也不会记住失败。

## 5. 写入标签（`pkg/tags` + `pkg/tidy`）

### 5.1 支持的格式

- 可写：**仅 MP3 与 FLAC**。`ErrUnsupportedFormat = "不支持的音频格式（仅支持 MP3 / FLAC）"`（`tags/tags.go:59`）；
  `tidy.TidyOne` 直接回「暂不支持写入 %s 格式」（`tidy/tidy.go:110`）；`nas.taggableExts` 只有 `.mp3/.flac`（`nas/tags.go:19-22`）。
- 格式判定按**魔数**，不信任扩展名：`SniffFormat`/`sniffBytes`（`tags/tags.go:84-111`，`fLaC` / `ID3` / `0xFF 0xE0`）。
- 索引层却认 14 种扩展名（`library/scanner.go:12-27`）→ WAV/APE/M4A/DSD 等「看得见、补不上」。

### 5.2 写了哪些键（白名单）

**MP3 = ID3v2.3**，帧集合在 `buildID3v2Tag` 里**硬编码**（`tags/id3v2.go:111-154`）：

| 帧 | 字段 | 编码 |
|---|---|---|
| `TIT2` / `TPE1` / `TALB` / `TCON` | 标题 / 歌手 / 专辑 / 风格 | `0x01` UTF-16+BOM（`:35-51`） |
| `TYER` + `TDRC` | 年份（**两个都写**，注释说飞牛读哪个无法本地验证，`:133-141`） | `0x00` ASCII（`:57-59`） |
| `TRCK` / `TPOS` | 曲序 / 光盘 | ASCII |
| `USLT` | 内嵌歌词（`lang="chi"`） | `:62-76` |
| `APIC` | 封面（图片类型 `0x03` front cover，空描述） | `:79-90` |

**没有** `TPE2`(ALBUMARTIST) / `TCOM` / `COMM` / `TLEN` / `TSRC` / `TPUB` / `TXXX` / MusicBrainz。

**FLAC = Vorbis Comment**，白名单 `managedVorbisKeys`（`tags/flac.go:32-45`）：
`TITLE/ARTIST/ALBUM/GENRE/LYRICS/UNSYNCEDLYRICS/DATE/YEAR/TRACKNUMBER/DISCNUMBER`。
- 写入时只写 **`DATE`**，不写 `YEAR`（`flac.go:157-161`）；读时两者都认（`:315-373`）。
- vendor 固定 `"fnmusic"`（`flac.go:288`）。
- 封面 = `PICTURE` 块，`picType=3`（`flac.go:185-203`）。
- **没有** `ALBUMARTIST` / `COMPOSER` / `TRACKTOTAL` / `DISCTOTAL`。

「只写目标播放器读得到的键」这种约束**确实存在**，但形式是「白名单硬编码」而不是可配置策略。
`mergeTextFields`（`tags/tags.go:150-180`）会在写入前把 **meta 里没传的** Title/Artist/Album/Genre/Lyric/Year/Track/Disc 从文件读回来，
因为两种容器都是「删掉受管字段按 meta 重建」。

### 5.3 幂等与重复清理

- **MP3**：整体重建 —— `skipExistingID3`（`id3v2.go:189-217`）跳过并丢弃**全部**旧帧，只保留音频。
  ⇒ 受管字段天然只有一份，**但未受管的旧帧（自定义 TXXX、ReplayGain、cue 等）一律丢失**。
  只处理 ID3v2，**不处理文件尾部 ID3v1，也不处理 APE 标签**（会被原样留在文件里，可能造成读到的值与写入值不一致）。
- **FLAC**：`mergeVorbisFields`（`flac.go:129-169`）先丢弃受管 key 再追加 ⇒ 受管字段不重复；
  ⚠️ 但重建时**多个 PICTURE 块只保留第一个**（`flac.go:259-296`），front/back/artist 三图会丢掉两张；
  **PADDING 块全部丢弃**（`:271-272`）⇒ 每次写盘文件长度都变。
- 封面保留：MP3 在 `meta.Cover` 为空时读回旧 APIC（`id3v2.go:165-172`）；FLAC 同理复用第一个 PICTURE。
- 写盘原子性：`atomicRewrite`（`tags/tags.go:206-252`，临时文件 `.fntag-*` + Sync + Rename + 保留权限）；
  FLAC 走同一入口。
- 外挂文件：同名 `.lrc`（`tidy/tidy.go:187-198`）、逐曲同名图（`:201-213`）；
  ⚠️ 但 `nas/tags.go:162` 与 `downloader.go:553-558` 的 `.lrc` 是 `os.WriteFile(...,0644)`，**非原子**。
- 触发重扫：`tags.TouchForRescan`（`tags/rescan.go:28-39`，只 `os.Chtimes` 改 mtime，
  因为飞牛按「路径 + mtime/size」做增量指纹，只写 `.lrc` 不会触发重读）。

### 5.4 封面与歌词的获取

- 歌词三级：① 平台 ID 直取（`fetchNetEaseLyricByID` `aggregator.go:502-525`）；
  ② 网易 cloudsearch 逐条核验（`fetchNetEaseLyricBySearch` `:527-584`）；
  ③ 酷狗歌词引擎按时长挑最近候选（`fetchKuGouLyricStrict` `:586-687`）。
  统一入口 `FetchLyric`（`aggregator.go:691-729`）。
- 封面：`security.FetchImage`（`security/image.go:29-82`）——SSRF 校验、逐跳重定向校验、12MB 上限、
  **按魔数**只认 JPEG/PNG/GIF/WEBP、UA 固定、可选 Referer。
  `tidy.TidyOne` **刻意不下载封面**（`tidy/tidy.go:159-162`），因为 `Item.CoverBytes` 是 `json:"-"`，
  HTTP 调用方只能把字节传进来（`security/image.go:7-10` 记录了这个缺口是 2026-09-18 端到端测试才暴露的）。

## 7. 明确的短板（按「值不值得用参考项目替换」排序）

1. **零上游限速 / 零缓存 / 零重试**（`aggregator.go:84-86`）。
   只有一个 8s 超时的共享 client，没有 sleep、没有令牌桶、没有并发闸门、没有退避重试。
   一次「补全 200 首」最坏会产生 ~800 次上游请求，且同一首歌重复补全时再打一遍。
   → 参考项目若有限速器 + 请求缓存，这是最高价值的替换点。

2. **`pkg/match` 没接进刮削链路**。
   `variantPattern`（版本标记）、`IsVariant`、`RejectReason`（时长校验）、`Similarity`（0.72/0.85 阈值）、`PickBest`（正式版优先）
   这一整套能力，只被 `monitor/pipeline.go:98` 和 `push/push.go:254-262` 使用；
   `complete` 与 `tidy` 完全不用（grep 确认：`complete/` 下无 `match.` 调用）。
   刮削主判据退化为 `MatchByNameSinger` 的「归一化后完全相等」（`search/qualities.go:123-144`）。

3. **没有时长校验的主命中路径**。
   `complete.resolveOne`（`complete.go:382-402`）只用 `MatchByNameSinger` 定命中，
   时长只在**借元数据**时校验（`sameRecording`，`complete.go:501-514`，容差 `max(10s,15%)`）。
   ⇒ 同名不同版本（原唱 vs 翻唱 vs Live）可以直达写入，`FilterSong`/`RejectReason` 那套防护不在这条路上。

4. **版本标记在解析阶段就被丢弃**。
   `bracketRe`（`nameparse.go:81`）删掉 `(Live)`/`(Remix)`/`(Acoustic)` 且不落字段，
   之后链路再也没有「这是不是改编版」的信息 —— 即使 `match.variantPattern` 有能力判断。
   `nameparse.Result` 也缺 version / quality 字段。

5. **没有「搜索结果反推校验文件名」**。
   只有单向「文件名 → 搜索词 → 严格相等」。平台标题带后缀时不命中（`complete.go:406-408` 注释承认），
   兜底是让 AI 从候选里挑（`pickByAI` `complete.go:911`，候选上限 20，`complete.go:908`），
   而 AI 兜底在 API 层**默认开启**（`api/library_complete.go:397-431`）⇒ 正确性依赖模型，且产生费用。

6. **无负缓存 / 无失败记忆**。
   搜不到、匹配不上、AI 判失败都不留痕：`complete.Resolve` 每次重搜全平台；
   `enrichIndexTags` 读失败只 `MarkTagRead` 不再重试（`api/features.go:362-397`）。
   `albumMetaCache` 无 TTL、溢出**整体清空**（`album_qq.go:62-64`），命中率不稳定。

7. **AI 调用无缓存、无限速、无预算闸**（`ai/ai.go`）。
   同一文件名重复解析会重复计费；只有 20s 超时（`ai.go:36-42`）与「直连↔代理」一次回退（`ai.go:952-985`）。
   用量只是记账（`ai.go:827-902`），不拦截。

8. **格式支持窄 + 标签键窄**。
   只有 MP3/FLAC 可写（`tags/tags.go:59`、`nas/tags.go:19-22`），索引却认 14 种扩展名（`library/scanner.go:12-27`）。
   MP3 白名单只有 9 类帧（`id3v2.go:111-154`），无 ALBUMARTIST/COMPOSER/TPE2/TSRC/MusicBrainz；
   处理 ID3v1 与 APE 标签的代码不存在。

9. **破坏性重写带来的隐性数据丢失**。
   `skipExistingID3`（`id3v2.go:189-217`）丢弃全部未受管帧；
   FLAC 重建时**多 PICTURE 只留第一个**、PADDING 全丢（`flac.go:259-296`）。
   「同字段多份」的问题不存在（因为整体重建），但「同字段之外的旧数据全丢」是真实风险。

10. **封面能力单薄**。
    `complete` 只取命中那条的 `Cover`（`complete.go:719-726`），无「按专辑取图 / 多图并存 / 图片质量选择」；
    `/api/library/cover-candidates` 只给候选不下载（`api/features.go:154-240`，打分仅「曲名完全等 +2 / 歌手包含 +1」）；
    `/api/tidy` 要求调用方给 `cover_url`（`api/features.go:88-107`）。

11. **进度与可观测性缺口**。
    `/api/tidy` `onProgress=nil`（`api/features.go:109`）；建索引串行 500 首无进度（`features.go:362-397`）；
    `HandleDuplicates` 的 `reclaimable` 是 O(n²) 内层循环（`api/features.go:526-536`）。

12. **重复实现与不一致**。
    - `dedupe.go` 自己切 `" - "`（`tidy/dedupe.go:122-127`），不走 `nameparse`。
    - 「歌名+歌手」的归一化有两套：`search.normalizeForMatch`（`qualities.go:53-80`）与
      `match.NormTitle/NormArtist`（`match.go:135-156`），判据不同。
    - 相似度匹配在 `push`、版本过滤在 `monitor`，与刮削链路三套并行。

13. **硬编码项**（替换/配置化时的清单）：
    平台顺序 `DefaultPlatforms = {wy,tx,kg,kw}`（`complete.go:103`）、主力平台 `PreferredPlatforms`（`complete.go:88-93`）、
    `Concurrency=2`（`complete.go:208-209`）、`TidyBatch concurrency=2`（`tidy.go:244`）、封面下载并发 4（`features.go:90`）、
    `maxMatchCandidates=20`（`complete.go:908`）、无损判定阈值 500 kbps（`search/quality.go:96-108`）、
    各平台页大小（`complete.go:386` 的 10、`qualities.go` 的 40、`features.go` 的 10）、
    单次上限 500（`features.go:62-65`）/ 200（`library_complete.go:286-293`）/ 30（默认 limit）。

14. **genre 来源单一**。
    只有 QQ 专辑详情给真实 genre（`complete.go:443-452`），其余平台不给；
    酷狗/酷我搜索响应不带年份与曲序（注释 `complete.go:357-361`）⇒ 为了「字段更全」不得不继续搜后面平台，成本翻倍。
    AI 推断风格只是兜底（`inferGenre` `complete.go:786-809`，长度 >12 或含标点即丢弃）。

## 附：与刮削链路相邻的两个包

- **`pkg/library`**：只做「文件枚举 + 索引」，**不读标签**（`library/scanner.go:62-210`）；
  索引 JSON（`library/index.go:102-109`）、变化判定 `(size, mtime)`（`:513-525`）、
  枚举不完整禁止删记录（`:559-599`）。它是刮削的「输入清单」，不是刮削本身。
- **`pkg/monitor`**：是「榜单/歌单 → 下载」的发现器（`monitor/pipeline.go:167` `BuildPlan`），
  用 `match.RejectReason` 做版本与时长过滤（`pipeline.go:98`），**不写标签**；
  与刮削的关系是「决定下不下、下哪一版」，下载完成后再由 `downloader.applyTags` 写入。
