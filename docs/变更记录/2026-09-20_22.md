#### 下一轮待办（用户已定方向，本轮**未实现**）

**A. 飞牛重扫频率：3 分钟 → 10 分钟**（用户 2026-09-22 明确选择「调得更安静」）

现状（`backend/pkg/fnos/rescan.go`）：`rescanDebounce = 30s`、`rescanMinGap = 3min`，
全部入口共用同一个进程级调度器，**上限 = 每 3 分钟 1 次** `POST /shared-library/scan-all`。
用户问「音乐任务为什么一直扫描，这个项目在一直触发吗」→ 是我们在触发，且有三个破口：
① `lastRun` 只在内存，**进程重启归零**；② 最小间隔从**发起**计时（不是完成），
而我们**从不查询**飞牛那边扫完没有 —— 单次全量若超 3 分钟就首尾相接；
③ 连续下载时 debounce 被反复推后，一空闲立刻补扫。
要做的：`rescanMinGap` 3min → **10min**；`lastRun` 持久化；间隔改为按「返回后」计时。

**B. 封面：飞牛不显示（按已查证据修，用户暂不提供样本）**

关键事实（见 §4.10 与本节背景）：**我们在界面看到的封面并不来自文件** ——
下载队列显示的是平台 CDN 的 `song.cover`（URL），NAS 页的 `/api/nas/cover` 有**目录级兜底**
（`cover.jpg`/`folder.jpg`/`front.jpg`），所以「我们能看到」证明不了文件里有封面。
而参考实现（`docs/参考项目/music-tidy/.../tidy_engine.py:1563`）明确：
**飞牛只读内嵌封面，不认逐曲同名 .jpg**。已查出的三个缺陷：
① 只对 MP3/FLAC 写内嵌（ogg/ape/wav/m4a 完全不写且不写 sidecar）；
② 抓封面**静默失败**（webp 被丢 —— `downloader.detectImageMime` 只认 jpeg/png/gif，
而 `security/image.go` 认 webp；Referer 硬编码 music.163.com）；
③ **MP3 二次写标签会删掉已有 APIC**（`pkg/tags/id3v2.go` 是「丢弃旧 ID3 + 只重建受管帧」，

**教训（已写进 §3.3.3）**：**用户抱怨某个术语时，不能只改前端。**

### 上一轮（2026-09-21 深夜 ㉕）：**修掉「点过停止更新，订阅就再也下不动歌」（v2.1.13）**

这轮本来是「按用户口述的「一键订阅」规格核对一遍 + 把热编辑页面打开给他看」，
**核对过程中撞出一个真 bug** —— 而且正好破坏用户最在意的那条需求
（「停止后想恢复，再点一次订阅就行」）。

**现象**：开发环境里跑订阅流程时顺手查后端状态，发现该监控的 `auto_download`
从 `true` 变成了 `false`（不是我改的）。

**根因**（`backend/pkg/monitor/http.go` 的 PATCH 分支）：

```go
// 修复前 —— 看着像「值变了才改」，实际语义是「没传也会改」
if patch.AutoDownload != m.AutoDownload { m.AutoDownload = patch.AutoDownload }
if patch.Embed != m.Embed { m.Embed = patch.Embed }
m.Enabled = patch.Enabled
```

请求里**没有** `auto_download` 时，struct 解出来是零值 `false`，与当前值 `true` 不等
→ 走进分支 → 被覆盖成 `false`。**「没传」和「传了 false」在 struct 里不可区分**，
所以 `!=` 这个写法方向就是反的。

**影响链**：点「停止更新」只发 `{enabled:false}` → 顺手把「自动下载」关掉；
点「恢复更新」也只发 `{enabled:true}` → **带不回来**。
界面上照旧显示「已订阅」，后台其实已经不下载了 —— 不报错、不影响播放，**极难自己发现**。

**修复**：额外解一遍请求体成 `map[string]json.RawMessage`，按「键有没有显式出现」判断：

```go
var present map[string]json.RawMessage
_ = json.Unmarshal(raw, &present)
has := func(k string) bool { _, ok := present[k]; return ok }
...
if has("auto_download") { m.AutoDownload = patch.AutoDownload }
if has("embed")         { m.Embed = patch.Embed }
if has("enabled")       { m.Enabled = patch.Enabled }   // 不带 enabled 的局部更新也不该把监控停掉
```

**这就是「局部更新」的正确实现方式** —— 以后往 `Monitor` 上加任何 bool 字段都照这个写，
**别再用 `!=` 判断**（`omitempty` 解决不了：它只能省掉出站字段，管不了入站）。

**顺带补上「老数据自愈」**：界面上**没有单独改 `auto_download` 的入口**
（只有「新建监控」表单里有那个复选框，已存在的改不了；监控也**没有删除按钮**，
`MonitorAPI.remove` 有接口但没接 UI）→ 已经被这个 bug 关掉的订阅，用户自己救不回来。
所以 `frontend/src/services/subscribe.js` 的 `setSubscriptionEnabled` 改成：
**恢复更新时主动把订阅该有的配置重新断言一遍**（`{enabled:true, auto_download:true, embed:true}`），
停止时只带 `{enabled:false}`（不去动配置）。这样老订阅点一次「恢复更新」就自愈。

**测试**：
- 后端 `backend/pkg/monitor/http_patch_test.go`（新建）：`TestPatchMonitorKeepsUntouchedBoolFields`，
  5 组断言 —— ① `{enabled:false}` 保住 `auto_download`/`embed` ② `{enabled:true}` 也保住
  ③ 显式传 `false` 要生效（证明不是「一律忽略」）④ 不带 `enabled` 的更新不该停掉监控
  ⑤ 从 store 重读确认已持久化。
- 前端 `frontend/src/services/subscribe.test.mjs` +4 个用例：停止只发 `{enabled}`、
  恢复重新断言、推送任务回传完整字段、无 id 跳过。

**端到端证据（三层，都是真跑）**：
1. **开发环境打接口**：`PATCH {enabled:false}` → `auto_download` 保持 `true`。
2. **浏览器真实操作**：精选歌单 →「订阅更新」→ 按钮变「已订阅 + 停止更新」→ 点「停止更新」
   →「已暂停 + 恢复更新」→ 点「恢复更新」→「已订阅」；**每一步之后查后端**，
   `auto_download` 全程 `true`。
3. **包内二进制行为验证**：把 `yinshu-ai.fpk` 里的二进制解出来跑在 `:8901`，
   建监控 → 打 `{enabled:false}` → 断言 `auto_download` 仍 `true`。
   ⚠️ **这一步不是多余的**：本修复**没有新增任何字符串字面量**（只是换了判断方式），
   `grep` 找不到能当标记的符号 —— **只有把包里的二进制跑起来打接口，才能证明它真带上了修复**。
