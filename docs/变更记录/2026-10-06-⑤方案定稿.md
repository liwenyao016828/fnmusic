# ⑤「洛雪源进下载源池」方案定稿（用户 2026-10-06 拍板）

## 拍板结果：**方案 (b) —— 搬到服务端 Node 子进程**

用户在 (a) 前端取链回传 / (b) 服务端 Node 子进程 / (c) 兜底解析器 三选一中选了 **(b)**。
这意味着**故意破掉**原来那条约束「后端不执行第三方 JS」—— 记录在案，不当作 bug。

## 但必须先说清 (b) 能买到什么、买不到什么

**买不到：搜索。** 洛雪脚本的契约里只有 `getMusicUrl`（给一条**已知**曲目解析直链）：
- 前端集成 `frontend/src/engine/lx-runtime.js` 只暴露 `getMusicUrl`，用 `new Function` 求值脚本（`:468`），
  以 `lx.on('request', …)` 收请求，提供 `lx.request`（`:294`）、`lx.send`（`:367`）。
- 后端 `backend/pkg/bridge/bridge.go` 的 `ResolveRequest` 是 `Platform` + `Songmid`/`ID`/`Hash` —— **解析**。

下载源池那一步要的是「按歌名+歌手+时长**并发找**同名曲目」= **搜索**。
**所以「洛雪当池里的搜索源」按字面做不到，与执行位置无关** —— 这一点在 (a)/(b)/(c) 之间是一样的。

**买到了：不依赖页面。** 现在洛雪只能在浏览器里跑，曲率窗口一关就不干活；
搬到服务端 Node 子进程之后，它**在页面关闭时也能解析直链**。这是 (b) 真正的价值。

## 因此 (b) 的交付物（与 (c) 同角色、不同执行位置）

**服务端 lx 解析器**：当「下载源池的候选」和「曲目自己平台」都拿不到直链时，
由服务端 Node 子进程里的洛雪脚本补一个 URL。**池里的搜索仍然由 musicdl 平台负责**（现状不变）。

## 硬约束（不能因为换了执行位置就丢）

1. **子进程挂了不能影响曲率** —— 解析器不可用时，下载链路照常回落（与 sidecar 掉线的处理一致）。
2. **脚本目录由用户提供** —— `preset_sources/` 里只有 `README.md` + `demo_template.js`（无真实音源脚本），
   所以脚本位置必须可配置，不能假设仓库里有。
3. **不引入 Go 第三方依赖** —— 宿主进程是 Node，Go 侧只做进程管理与 HTTP，`go.mod` 保持零依赖。
4. 版本号四处同步；新接口登记 `catalog.go`。

## 尚未验证、动手前要确认的点

- 洛雪脚本在 **Node（无 DOM）** 下能不能跑起来 —— 具体缺哪些全局（`document`？`window`？）要拿真实脚本实测，不能凭 `lx-runtime.js` 推断。
