### 1. 榜单与在线歌单：满量显示 + 试音跨源兜底

**根因**：`backend/pkg/intercept/vchart.go` 的 `chartPlaylist` 过去对整榜跑
`i.playableOnly(ctx, ref.Source, tracks)`，后者用 `pool.ResolveMany` 逐个平台解析，**解析不出直链的直接丢弃**
—— 网易热歌榜 100 首实测只剩 36 首进榜。用户口径（m00064）：「100 首就显示 100 首，播不响的交给取音层」。

**改法**：`chartPlaylist` 去掉 `playableOnly`，改走新增的 `dedupeTracks`（`vplaylist.go`：`Normalized()` + 按
`RealID` 去重 + 跳过空 `PlatformID`/`Title`），再截断到首数；`neteasePlaylist` / 在线专辑同理，不再按可播性裁剪
（三处同一口径，`playableOnly` 保留但从榜单/歌单/专辑三条路退出）。

**缺的那半截**：显示满量以后，播不响的曲目需要别的源顶上来。`resolvePlayback`（`playback_quality.go:154`）
末尾挂 `resolvePlaybackFallback`（新文件 `backend/pkg/intercept/playback_fallback.go`）：native 失败、跨源无损分支也没救回来之后，
用 `rankedSources(ctx, title, artist, wantSec)` 找候选（只取前 `fbCandidates=3` 个非同 id 的），逐个 `ResolveLadder`。
缓存 `fbCacheTTL=30min` / 负缓存 `fbNegTTL=5min` / 上限 `fbCacheMax=1024`，总预算 `fbBudget=12s`；
⚠️ **超时的那次不写缓存**（`sctx.Done()` 分支直接 return nil），否则一次网络抖动会把「能播」钉死成「不能播」30 分钟。

### 2. 榜单显示首数（全局 + 按榜覆盖）

- `backend/pkg/config/config.go`：`AppConfig` 加 `ChartSize`（全局）与 `ChartSizes map[string]int`（按榜单 id），
  归一化走 `NormalizeChartSize`。**`normalizeChartSize` 返回 0 只代表「没填」，绝不能当「清空」用** —— 这是后面那个 bug 的伏笔。
- `backend/pkg/intercept/vplaylist.go`：新增 `chartSizeFor(chartID)`，`chartPlaylist` 用它截断。首数在**两边各算一次**是不行的，
  所以 `chartSizeFor` 是唯一入口，注释里写明理由。
- **真 bug（必看）**：`vPlaylistFor(guid, r)` 只按 `guid` 缓存 30 分钟（`vCacheTTL`），而截断发生在缓存之后 ——
  结果「改首数」要等缓存过期才生效。修法：榜单的 `cacheKey = guid + "#" + itoa(i.chartSizeFor(...))`，
  读写缓存都用 cacheKey，`pl.GUID` 仍用原 guid。同源问题在 `.dev` 联调时用户当场发现（改 60→20 没反应）。
- **前端**：`frontend/src/services/chartInject.js` 加 `chartSize`/`chartSizes` ref、`effectiveChartSize(key)`
  （优先级 = 单榜 > 全局 > `DEFAULT_CHART_SIZE`）、`setChartSize`/`setChartSizeFor`（null = 清）；
  `SearchView.vue` 加「显示首数」下拉（默认/20/30/50/100/200），卡片上点「N 首」按 `[20,30,50,100,200,0]` 循环。
  `loadConfig` 里用 `startEpoch !== writeEpoch` 与 `busy.value` 双闸，防「读回旧值盖掉用户刚点的」。

### 3. 设置保存互相覆盖（`mergeConfigPatch`）

**根因**：`backend/pkg/api/server.go` 的 `handleConfig` 里，「榜单首数」与「清空令牌」是两个独立 `if` 分支，
各自 `patch = next` 而 `next` 是 `cfgMgr.Get()` 的旧值 —— **同一次请求里后一个分支把前一个的改动整个盖掉**。
表现：「保存首数时把同请求里刚填的 token 丢了」「清空首数不生效」。
**修法**：新增 `mergeConfigPatch(next, patch)`（JSON 往返相并，patch 有内容的键覆盖 next，零值/空串不覆盖，
`json:"-"` 内部标记会被丢、调用方自己重新置位），两个分支合并成一个统一块。新增 `config_overwrite_test.go` 三例钉住。

另：`AppConfig.ChartSize/ChartSizes` 带 `omitempty`，0/空表与「没传」解码后无法区分，而 Update 是补丁语义。
加内部字段 `ChartSizeOverride bool `json:"-"``（只在 `/api/config` 流转、不落盘），overwrite 分支末尾置位。

### 4. 歌名修复（「补全整理 → 歌名修复」）

`backend/pkg/api/title_fix.go`：`GET /api/library/title-fix/scan` 扫「没歌名 / 占位词 / 歌名是文件名 / 太长 / TrackNN」，
`POST /api/library/title-fix/fix` 逐条 `suggestTitle` → `tidy.TidyOne(WriteMetadata)` → **`backup.NoteWithOld` 记旧歌名/旧歌手** → `MarkEnriched`。
`suggestTitle` 用 `ai.ParseName` + `ai.NameAppearsIn` **防幻觉**（AI 编出来的名字必须在文件名里出现过），兜底走 `tidyGuessTitle(nameparse)`。
最多 50 条/次；`s.aiReady()` 为假直接拒绝 —— 这是**修「没配 AI 也报修复成功」**：老逻辑在没有 AI 客户端时会静默回落到规则推断，
然后回 `ok:true`，用户看到「AI 修复成功」但名字没变。现在明确报「未配置 AI」。

`backend/pkg/complete/backup.go` 的 `BackupEntry` 加 `OldTitle/OldArtist`（json `old_title`/`old_artist`），
`Note` 改为转调新 `NoteWithOld` —— 修复记录列表要显示「旧 → 新」，只存新值不够撤回展示。

### 13. 「补全整理」整页空白（重要坑）

用户 m00735 / m00761：「补全整理看不到页面，只有里面的补全，查重等导航栏」/「还是看不到「补全整理」五个分段的内容啊」。
**根因**：`TidyView.vue` 的模板里引用了**未定义**的标识符 `planStreaming`（模板求值抛错 → 整段内容不渲染，只剩外壳导航）。
**教训（必记）**：这类错误 **`vite build` 不报、`compileTemplate` 也不报**，只能用
`compileScript().bindings` 与自己扫的模板标识符做差集才能抓到。
为此保留 `frontend/check-tpl.mjs`（纳入仓库）：用同一套 AST 比对模板引用 ↔ setup 绑定，
以后改模板先跑它。同类前车之鉴：`downloadManager.js` 的 TDZ（见 2026-10-24 v2.18.1）。
