### 上一轮（2026-09-19 上午 ⑮）：**修扫码登录两处根因 + 发现监控「自动」是断链的**

用户贴了 5 张真机截图问「都是什么情况」。逐个查证，**全部是真实缺陷，不是使用问题**。

#### ① 网易云扫码：`type=1` → `type=3`（~~真 bug，已修~~ ⚠️ **本结论已被当晚的 ⑯ 推翻**，见 §4.9 坑 A 与上方 ⑯ 条目）

二维码能显示，手机扫码后 App 弹「请切换其他登录方式或升级新版本再试用」。
`type` 是登录端类型，`1` 是 PC 旧版、已是废弃值；改 `3` 即可。

**为什么一直没发现**：服务端对 `type=1~10` **全都返回 200 + unikey**（我逐个探测过），
所以「申请 key 成功」看不出任何异常，**只有真人扫码才知道**。

同时补上 web 端必需的 `chainId` 参数。

#### ② QQ 扫码：漏了 `check_sig` 这一步（真 bug，已修）

「已扫码，请在手机上确认」之后卡死，报 `QQ 授权没有返回 p_skey`。

老流程直接拿跳转地址请求就指望响应头带 `p_skey`，**现在不会了**。
必须从跳转地址抠出 `uin` + `ptsigx`，再请求
`ssl.ptlogin2.graph.qq.com/check_sig` 才能换到 `p_skey`。

⚠️ **关键教训**：这段代码是**照 `fnmusic-flow` 移植的，而 flow 自己也漏了这一步**。
**「有参考实现」不等于「参考实现是对的」** —— 要找**活跃维护的**（这次是
`QQMusicApi` 与 `@neteasecloudmusicapienhanced/api`）。已写进 §9。

#### ③ 监控「待建基线」卡住（**架构缺陷，未修，已写进 §4.1**）

第一轮成功、之后每轮都失败。根因：**上报只在订阅那一刻发生一次**，
之后没有任何代码再上报，而 `takeDiscovered` 是**消费式**的 → 第二轮起必然取不到。

**结论：现在只有「手动跑一轮」能工作，「自动下载新增曲目」不可能发生。**
修法（前端定时上报 / 后端抓取通道）已在 §4.1 写清，**未实施**。

#### ④ 日志里 `/api/push/sources` 报「尚未连接网易云账号」

**这是正常的** —— 没登录就该报。不是故障。

#### ⭐ 最有价值的发现：我们的一个静默失败（**已修**）

它的错误处理里有：`content || reasoning` 回退 + 识别 `finish_reason === "length"`。

- **两段式**：先「意图解析器」（NL → 结构化 JSON），再推荐
- **「特征检索 → 候选 → LLM 挑」**：后端用 ffmpeg 解码 + ONNX 本地推理算出

- **「分组渐进筛选」**：候选太多时分批过滤

- **强约束措辞**：「你【必须】且【只能】从…绝对禁止伪造…否则将导致系统崩溃」

### 本轮（2026-09-18 深夜 ⑧）：**先预览后写**（批量补全，P1 收尾）

#### 为什么

补全会**真正改写用户的音频文件**。撤销是兜底，**主防线应该是「写之前让用户看一眼」**。

#### 做法：`pkg/complete` 拆成两阶段

原来 `Run` 一步到位（解析 + 写）。现在拆成：

| 函数 | 做什么 | 碰文件吗 |
|---|---|---|
| `Resolve(ctx, targets, opts, onProgress) Plan` | 定名 → 搜索 → 匹配 | **不碰** |
| `Execute(ctx, plan, opts, onProgress) Summary` | 取歌词/封面 + 写标签 | 会 |
| `Run` | 上面两步串起来（保持兼容） | 会 |

`PlanItem` 里除了展示字段，还**记下匹配到的曲目标识**（`source/songmid/hash/duration/coverURL`）。

#### ⚠️ 关键：执行用的是**预览时那份计划**，不重新搜

```go
// ⚠️ 记下**匹配到的曲目标识**，而不是让执行阶段重新搜一次 ——
// 否则搜索结果变了、AI 挑得不一样，用户就会「批准了 A、结果写了 B」。
```

同理前端执行时传回的是 `plan_id` 而不是重新提交目录。

#### 接口

```
POST /api/library/complete {dir, limit}                 直接跑（兼容只调接口的调用方）
POST /api/library/complete {dir, limit, dry_run: true}  只出预览 → 返回 plan_id + 逐条对照
POST /api/library/complete {plan_id}                    执行那份计划
POST /api/library/complete/cancel                       停止正在跑的任务（不再派发新曲目）
```

**任务可以停（v2.1.30 树内新增）**：一批最多 200 首、每首两次外网 + 改文件，分钟级；
以前一旦开跑就只能等（再点被 409 挡回），而它正在改用户的文件。
停止 = **不再开始新的曲目**：已写入的保留（要回退用撤销），正在写的那一首会写完 ——
写到一半中断会留下半个标签块，比不写更糟。没在跑时如实回「没有正在跑的补全任务」。
`cancelled:true` 说的是**任务本身**被停；`summary.cancelled` 说的是**有几首没处理**（不是失败）。

**计划只能用一次**（`pendingPlan.take` 取出即清空）——
重复执行没意义（第二次会因为不再缺歌词封面而空转），而且会让人以为「点了两次写了两次」。
计划也只保留**最近一份**：保留多份只会让人点错。

#### 前端

按钮点下去只出**预览表**（文件 → 匹配到的歌 · 平台 → 会写什么），
再点「确认写入 N 首」才落盘。表头写的是「即将写入（**还没有动过文件**）」。
底部提示「写入前会自动备份，可随时撤销」。

#### 验证（端到端实测）

| 步骤 | 结果 |
|---|---|
| 预览 | 2 首匹配到（晴天→tx、演员→wy），`nothing_written = true` |
| **预览后文件** | 仍是 **218 字节**、无 `.lrc`、**备份目录都没建** ✓ |
| 执行 | 补歌词 2 · 补封面 2；文件变 36,657 / 151,766 字节 |
| 同一份计划再执行 | 明确提示「这份计划已失效或已被执行，请重新预览」 |
| 撤销 | `restored=2, removed=2` —— 多文件撤销也对 |
| UI | 预览表内容正确、确认按钮文案正确；真实渲染 + 截图核对；JS 错误为空 |

单元测试新增 **2 组**，盯的是「先预览后写」的核心保证：
**没匹配上的项绝不碰文件、也不产生备份**（`TestExecuteSkipsUnmatchedWithoutTouchingFiles`）。

### 本轮（2026-09-18 深夜 ⑦）：**撤销上一次补全**（批量补全的前置）

#### 为什么先做这个

补全会**真正改写用户的音频文件**。规则再稳、AI 再准，也可能出现「整批都补错了」
（比如匹配到了另一个歌手的同名专辑）。**没有回滚手段的批量写文件功能，用户是不敢用的。**

#### 为什么是「整文件备份」而不是「记录改了什么再反向操作」

标签写入是**破坏性重写**（原子替换整个文件）。要反向操作就得精确还原原有的
ID3 帧顺序、文本编码、填充长度 —— 那比重拷一份文件脆弱得多，还原得不完美文件可能就坏了。
音频文件不算大，宁可多占点磁盘，也要保证「撤销」真的能还原。

#### 实现（`pkg/complete/backup.go`）

- `Backup.BeforeWrite(path)` —— 改写前拷一份原文件，**并记下当时有哪些 sidecar**（`.lrc`/`.jpg`）
- `Backup.AfterWrite(path)` —— 对比前后，记下**本次新建**的 sidecar
- `Backup.Commit()` —— 落盘 `manifest.json`；没备份任何文件时**不留空目录**
- `Restore(dir)` —— 先删新建的 sidecar、再还原原文件（顺序反了会让还原后的文件多出一份不属于它的 `.lrc`）

**备份目录**：`<dataDir>/ai_backup/<时间戳>/`，清单里记 `{original, copy, size, created}`。

#### ⚠️ 最关键的一条：**用户原有的 sidecar 不能被删**

补全只在「缺失时」写 `.lrc`，所以本来就存在的 `.lrc` **不是我们建的**。
撤销时把它删掉 = 毁用户数据。`BeforeWrite` 先快照、`AfterWrite` 再对比，
只有「本来不存在、这次才出现的」才会进 `created` 列表。
**这条有专门的用例盯着**（`TestRestoreKeepsPreexistingSidecar`）。

#### 其它安全设计

- **备份失败就跳过该文件** —— 不能「备份失败还继续写」，那等于悄悄剥夺了用户的回滚能力
- **还原失败时备份保留**，用户可以重试；只有全部成功才删备份目录
- **撤销只做一次**（没有「重做」），确认弹窗里明确说了
- **`undo_available` 从磁盘判断**而不是内存里的 summary ——
  服务重启后 summary 就没了，但备份还在，用户仍然应该能撤销

#### 接口

```
POST   /api/library/complete/undo   还原
DELETE /api/library/complete/undo   只删备份（确认不用还原了，释放磁盘）
```

（**想停掉正在跑的那一批**是另一个接口：`POST /api/library/complete/cancel` —— 见本节上方「任务可以停」。）

撤销后**必须刷新索引**：索引里的 `HasLyric`/`HasCover` 在还原后就过期了，
不刷新的话下一轮补全会因为「索引说有歌词」而跳过，用户会看到「撤销了但再也补不上」。
实现是用 `tidy.NeedsTidy(path)` **读实际文件**重新判定，而不是猜。

#### 验证（端到端实测）

| 步骤 | 结果 |
|---|---|
| 补全前 | 233 字节、无 `.lrc`、`undo_available=false` |
| 跑补全 | mp3 → 36,672 字节、生成 2,447 字节 `.lrc`、备份里出现 233 字节原件 |
| **撤销** | `restored=1, removed=1, failed=0` |
| 撤销后 | mp3 **回到 233 字节**、`.lrc` 已删、备份目录已清、`undo_available=false` |
| 再撤一次 | 明确提示「没有可撤销的补全记录」 |
| **索引刷新** | 撤销后 `has_lyric`/`has_cover` 回到空 → 再跑补全**能重新挑中**并补上 |
| UI | 「撤销上一次补全」按钮正确出现（真实渲染 + 截图核对），JS 错误为空 |

单元测试 **9 组**（`backup_test.go`），重点全是**「会不会误伤用户数据」**：
用户原有 sidecar 不被删、还原失败时备份保留、原文件被删能重建、多文件、nil/空目录不崩。

### 本轮（2026-09-18 深夜 ⑥）：AI 落地第四件 —— **歌词核验（P1）**

#### 为什么需要

`search.MatchByNameSinger` 只能保证**曲名歌手对得上**，**不能保证平台返回的歌词文件本身是对的**
（平台数据错标、同名前缀串味）。而**写错歌词比不写更糟** ——
用户会以为是真歌词，还失去了「缺歌词」这个可行动的信号。

#### 做法：**验证**用途，不是生成

参考实现 `analyze_song` 的定位：「只判断歌词与歌曲是否匹配，**不要提出修改歌手或歌名**」。

- **`ai.Client.VerifyLyric(artist, title, lyric)`** → `{match, confidence, reason, actual}`。
  送进去前先去时间码、截断 1500 字（核验看内容，不看时间轴）。
- **核验对象是「本地曲目自称的身份」**（`item.Title`/`Artist`）而不是命中候选的身份 ——
  这样既挡得住平台错标，**也挡得住「AI 挑错了歌」**（后者正是风险最高的那类）。
- 不通过就**不写**（宁缺毋滥），并记 `LyricRejected` + 原因。

#### 成本控制：默认只核验「AI 挑的匹配」

```go
shouldVerify := opts.AIClient != nil && lrc != "" &&
    (opts.UseAIVerifyLyric || r.MatchedByAI)
```

AI 挑的匹配风险最高、数量最少；对全部曲目核验会让 AI 调用量翻倍，
所以留了 `UseAIVerifyLyric` 开关（默认关）。

#### ⚠️ 写的时候踩到一个坑：`bool` 的零值又一次

第一版用 `var out LyricVerdict` 直接解 JSON。模型如果只回了个 `{}`，
`Match` 取零值 **false** —— 就被当成「判定不匹配」，**把好歌词全丢掉**。

必须区分「判定为不匹配」和「根本没判定」→ 用 `*bool` 接，`nil` 时返回 `ok=false`
（调用方按「没核验」处理，而不是按「不匹配」）。参考实现也是这么防的
（`if "match" not in obj: return {}`）。

> 这跟 P0-2 那个 `Enabled` 零值坑是**同一类问题**：
> **布尔字段的零值语义要想清楚**，尤其是「没有值」和「值为假」必须能区分。

#### 验证

- `pkg/ai` 新增 **3 组用例**（7 个子例），其中最关键的一条就是上面那个坑：
  **「模型只回 `{}` 时不能被当成不匹配」** —— 另有「JSON 里没有 match 但有别的字段」、
  「返回非 JSON」、「置信度越界要夹回 [0,1]」、「只有时间码没有正文时不发请求」
- 后端 **22 包全绿**；前端 71/71 + 构建通过
- 前端结果摘要新增一行：**「N 首歌词对不上，已跳过不写」** ——
  与「没取到歌词」分开显示，否则用户看不出为什么没补上

> ⚠️ **未验证**：`VerifyLyric` 的真实判断准确率。mock 只证明了「解析与防错逻辑正确」。

### 本轮（2026-09-18 深夜 ⑤）：AI 落地第三件 —— **搜索匹配消歧（P1）**

#### 要解决的问题

`search.MatchByNameSinger` 要求曲名归一化后**完全相等**，只能处理「同名同歌手」。
而平台返回的标题常带后缀（`晴天 (Live)`、`晴天 (原唱 周杰伦)`、`晴天（R&B版）`），
或者同名不同版本 —— 规则全都不认，结果就是**「搜到了但配不上，整首歌补不了」**。

#### 做法：复用 P0-1 的 judge 模式

- **`ai.Client.PickSongMatch(want, candidates)`**：给候选列表，AI 只输出**候选序号**或 `null`。
  候选由搜索给出，AI 不能引入候选外的任何内容 —— 输出范围被限制成有限集合。
- **`pkg/complete` 的搜索循环改造**：规则命中即停（不花 AI 的钱）；
  全平台都没命中时把候选**攒成池**，交给 AI 挑。
- 新增 `Options.UseAIMatch` 开关（`/api/library/complete` 默认开）；
  没配 AI 时 `PickSongMatch` 内部先判 `Available()`，直接返回 false。

#### 三个防错设计（挑错歌比没配上严重得多）

1. **候选编号从 0 开始显示** —— 参考实现也这么做。显示 1 起会让「模型回 0」产生歧义，
   而**差一位就是挑错歌**，会把别的歌的歌词封面写进用户文件。
2. **越界一律判失败** —— `pick < 0 || pick >= len(candidates)` 直接返回 false，宁可漏配。
3. **候选池截断到 20 条** —— 四个平台各 10 条就是 40 条，prompt 会明显变长也更贵；
   按平台顺序截断（前面的平台优先，那正是我们更信任的）。

#### 透明度：AI 判断的结果要能看出来

`ItemResult.MatchedByAI` 透出到接口，前端结果摘要里显示
「其中 N 首由 AI 判断匹配」。理由同评估文档 §7 第 6 条：**来源必须可分辨** ——
用户有权知道哪些结果是模型判断的，而不是规则算出来的。

#### 验证

### 本轮（2026-09-18 深夜 ④）：AI 落地第二件 —— **AI 生成命名正则（P0-2）**

#### 为什么让 AI 产出「规则」而不是「结果」

参考实现 `analyze_name_rule` 是这个思路里最好的一个：用户给一个文件名样例 + 一句解释 →
AI 产出**一条正则** → 之后整库按它解析、**不再调 AI**。

- 成本从「每首歌一次调用」降到「**每种命名习惯一次**」
- 产出物（正则）**透明、可检查、可手改** —— 用户看得懂
- 之后完全确定性、可测试

#### 落地位置

| 新增 | 作用 |
|---|---|
| `pkg/nameparse/rules.go` | `Rule` / `Store`（JSON 持久化）/ `ValidateRule`（**五道校验**） |
| `ai.Client.SuggestNameRegex(sample, desc)` | 把「样例 + 解释」转成正则 |
| `pkg/api/name_rules.go` | `GET/POST/DELETE /api/library/name-rules` |
| 前端「账号连接 → AI 大模型」面板 | 样例 + 解释 → 生成 → **可编辑的正则** → 校验 → 保存；已有规则可停用/删除 |

#### ⚠️ 安全关键：AI 产出的正则**必须回测**（`ValidateRule` 五道关）

正则来自模型，可能语法错误、可能匹配不上样例、可能提取不出字段，
甚至可能从别处「变出」内容。任何一道不过都**拒绝保存**：

1. 正则语法正确（能编译）
2. 组名在**白名单**内（`artist` / `title` / `album` / `track`）——
   拼错的组名不会报错，只会静默少一个字段
3. 至少含 `artist` 或 `title` 之一
4. 能匹配上样例（search 语义）
5. **提取结果必须出自样例本身** —— 同 `JudgeName` 的防幻觉思路

UI 上也**生成与保存分成两步**：AI 出的正则先显示给用户看（可手改），
确认后才落盘。直接存下去再让他在别处发现问题就晚了。

#### 用户规则优先于内置启发式

`nameparse.Store.Parse()` 先试用户规则，没命中才回落到内置启发式 ——
用户规则是**用户显式定义的意图**，启发式只是我们猜的。
`pkg/complete` 通过 `Options.NameRules` 接上（`resolveName` 里用）。

#### 踩到一个坑：`Enabled` 的零值

第一版规则结构体用 `Enabled bool`，结果「AI 生成 → 保存」出来的规则**默认不生效**
（零值 false），用户会以为功能坏了。测试直接把这个暴露了出来。
改成反向字段 **`Disabled bool`** —— 零值 = 启用，符合直觉。

#### 验证

- `pkg/nameparse` 新增 **11 组用例**，其中重点是**「坏正则挡不挡得住」**：
  空正则 / 语法错 / 组名不在白名单 / 没有 artist 也没有 title / 匹配不上样例 /
  提取结果不在样例里 —— **全部被正确拒绝**
- **`TestRuleBeatsHeuristic`**：同一个文件名 `【无损】周杰伦_晴天_2003.mp3`，
  启发式给 `晴天_2003`、规则给 `晴天` —— 把「规则不是锦上添花」这件事固化成用例
- **端到端实测**：注入一条**无标签**的索引记录 + 保存对应规则 → 跑补全 →
  解析出 `歌手=周杰伦 歌名=晴天` → **搜索匹配成功（tx）→ 歌词与封面都补上了**。
  用启发式的话歌名会是 `晴天_2003`，`MatchByNameSinger` 归一化后对不上，整首补不了。
- API 实测：列表 / 保存 / 校验（dry_run）/ 三种拒绝路径 / 未配 AI 时的明确提示 —— 全部正确
- 前端真实渲染 + 截图核对；JS 错误为空
- 🧹 测试痕迹已清理（规则、测试音频、索引已从 `.bak` 恢复）

### 本轮（2026-09-18 深夜 ③）：AI 落地第一件 —— **文件名判名（P0）**

用户：「不做 ai 生成歌词，其他开始吧」。按 `docs/AI 能力评估.md` 的顺序从 P0 开始。

#### 现状缺口（这是本轮的起点）

项目原来只有两条路：`pkg/complete` 里 **20 行**的 `guessFromFilename`（只会在 `" - "` 上切一刀），
和 `pkg/ai.ParseName`（直接交给大模型）。**中间缺了规则层** ——
结果是「要么用最土的规则，要么花 AI 的钱」。

#### ① 新增 `pkg/nameparse`：规则层 + **主动标可疑**

这是本包最重要的设计，也是从参考实现 `_llm_should_rescue` 学来的：

> 「规则拆不出来」好办（字段为空，一看就知道）；
> **危险的是「规则以为自己对、其实错了」** ——
> 把「好听的歌曲推荐」当成歌手，字段非空、看着正常，却会悄悄写进用户的标签。

所以规则层要能自己说「这次我不确定」。`Result.Suspect` + `Result.Reason` 就是干这个的。

标可疑的四种情况（都对应真实的坏命名）：

| 触发 | 例子 |
|---|---|
| 歌手位置命中噪声词 | `好听的歌曲推荐-下山 - 麦小兜.mp3` |
| 开头有方括号内容 | `【无损】周杰伦 - 晴天.flac` |
| 中英文混排（方向说不准） | `周杰伦 - JayChou.mp3` |
| 整串命中噪声词 / 无分隔符且超长 | `好听的歌曲推荐合集一百首经典老歌.mp3` |

另外**歌手位置是噪声词时不是「左右互换」而是「丢掉前缀再切一刀」** ——
换过来只会让歌名变成「车载音乐」这种更离谱的结果。

**候选（`Candidates`）**：两段命名会同时给出「左歌手右歌名」和互换两种解释，
交给上层挑（包括交给 AI 挑）。AI 只做「挑对/纠正」比让它凭空认准得多。

#### ② 新增 `ai.Client.JudgeName(filename, candidates)`：候选消歧 + **防幻觉硬校验**

参考实现 `judge_name` 的注释写得很直白：「模型的作用是『挑对/纠正』而不是重新创作」。

**关键在「防幻觉不是提示词的事」**：光靠 prompt 说「不许编」不够，返回前**自己校验**——
`artist` / `title` 必须能在原始文件名里找到（忽略大小写、空格与标点，因为
文件名可能是 `Jay Chou` 而模型回 `JayChou`）。校验不过一律返回 `ok=false`，
调用方沿用规则结果。**宁可漏补，也不把模型的胡言写进用户文件。**

#### ③ 接进 `pkg/complete`：优先级 **索引 > AI > 规则**

`resolveName()` 取代了原来的 `guessFromFilename`：

1. 索引里 title+artist 都有 → 直接用，不折腾（它来自文件标签/上次整理，比猜的准）
2. 缺的部分先用规则填
3. **只有 `nameparse.NeedsAI()`（字段空 **或** 自认可疑）时才请 AI** ——
   规则能拆的不花这个钱
4. AI 只补索引缺的那部分，不覆盖索引已有的值

`Options.UseAINameJudge` 是开关（`/api/library/complete` 里默认开）；
没配 AI 时规则照常工作。

#### 验证

- **`pkg/nameparse` 新增 6 组用例**：常规命名、4 种可疑场景、候选生成、`NeedsAI` 判据、序号、边界
- **`pkg/ai` 新增 4 组用例**，重点是**「模型答错时挡不挡得住」**而非「答得对不对」：
  歌手不在文件名里 / 歌名被换成另一首 / 判不出来 / 返回的不是 JSON —— **全部被正确挡下**
- **`pkg/complete` 新增 3 组用例**：规则层与索引层的优先级
- 后端 **22 个包测试全绿**（原 21 + 新增 `nameparse`）；`gofmt` / `go build` / `go vet` 干净

> ⚠️ **未验证**：`JudgeName` 的真实准确率 —— 测试用的是 mock server，
> 只证明了「幻觉挡得住」，没证明「挑得对」。要验证得配真实 API Key 跑一批已知答案的歌。

### 本轮（2026-09-18 深夜 ②）：对照参考实现 `music-tidy v1.14.0` 校正 AI 评估

用户给了 `music-tidy-1.14.0.fpk` 并说「看他用 AI 做了什么，可以照抄」。
解包核对后**我修正了自己上一轮的一部分判断** —— 它的保护措施比我预想的扎实。

**解包方式**（FPK 是 gzip 包，里面还有一层 `app.tgz`）：

```bash
tar -xzf music-tidy-1.14.0.fpk && mkdir app && tar -xzf app.tgz -C app
```

**它用 AI 做了什么**（实测：`server/ai_llm.py` **675 行 / 8 个方法**，
`tidy_engine.py` **11 个调用点**）：

| 方法 | 用途 |
|---|---|
| `recognize(filename)` | 文件名 → artist/title/style |
| `judge_name(filename, candidates)` | **从规则切出的候选里挑**正确的一组 |
| `analyze_name_rule(sample, desc)` | **用户给样例+解释 → AI 产出正则规则** |
| `analyze_song(artist, title, lyric)` | **核验已有歌词是否与歌名歌手匹配**（验证，非生成） |
| `dedupe_decide(group, gtype)` | AI 决定查重保留哪版 |
| `generate_lyric(artist, title, style)` | AI 生成带时间码歌词 |
| `cover_prompt` + `generate_image` | AI 文生图做封面 |

#### 三件直接可搬的（已写进 `docs/AI 能力评估.md` §2）

**① 「结果必须来自输入」的防幻觉约束** —— `_llm_rescue` 的注释写得很直白：
「用『结果必须来自文件名』挡住幻觉……判不出、或给了文件名里没出现的歌手歌名，
一律返回 `{}`，上层沿用规则结果」。`judge_name` 的 prompt 也要求
「歌手与歌名都只能是文件名里出现过的文字，绝对不许换成另一首歌」。

**② 「让 AI 生成规则」而不是「让 AI 做判断」** —— `analyze_name_rule`：
用户给一个文件名样例 + 一句解释 → AI 产出**一条 Python 正则**（带命名分组）→
**校验**（`rlm-warn`：「AI 生成的规则未通过校验，请在下方修正正则」）→
**用户可手改** → 之后整库解析走正则、**不再调 AI**。
> 💡 成本从「每首歌一次调用」降到「每种命名习惯一次」，产出物透明可编辑。**这是本轮最大的收获。**

**③ 触发条件用「规则自认可疑」而不是「字段为空」** —— `_llm_should_rescue`：

```python
return bool(not meta.get("title") or not meta.get("artist") or meta.get("suspect"))
```

它的注释解释了为什么要加 `suspect`：**旧版只在字段为空时才调模型，
像「好听的歌曲推荐-下山 - 麦小兜」这种两头都错、但两头都非空的解析，永远进不了 AI 兜底**。
> 💡 这比我原来写的「规则失败才兜底」更好 —— **「规则以为自己对、其实错了」才是最危险的**。

#### 我**修正**的判断

- **文件名 AI 兜底**：从 P1 提到 **P0**（它是最有价值的一环，且参考实现已给出完整做法）
- **新增两个我原先漏掉的**：`analyze_name_rule`（AI 生成正则）、`analyze_song`（歌词核验）
- **AI 决定查重**：从「不做」软化为「**规则决定、AI 只解释**」——
  它给的判断依据（音质/时长/码率/格式/路径）全是已有字段，规则能确定性算出来；
  但它的 `reason` 字段有价值（用户看报告时「为什么保留这个」比「保留哪个」更有用）
- **AI 生成封面**：从「没考虑」提到「可做，但必须标注 + 默认关」

#### 我**坚持**的判断：不做 AI 生成歌词

参考实现做了，而且做得挺克制（只在刮削失败且无 `.lrc` 时、标 `lyric_source: "llm"`、
UI toast「歌词由 AI 生成（时间码为估算值）」、批量入口确认框事先说明）。
但我仍建议不做，理由写在 `docs/AI 能力评估.md` §5，核心三条：

1. **时间码是估算的、不会同步** —— 它自己的注释就承认了。不同步的歌词在播放器里没价值
2. **产出物读起来像真的** —— prompt 明写「请……创作合理、连贯……的中文歌词」，
   主副歌结构齐全，用户**一眼分辨不出**；而 `lyric_source` 只在写入那一刻 toast 一下，
   **事后翻看 `.lrc` 文件是看不出来的**
3. **「没有歌词」比「错的歌词」更好** —— 编造的歌词会污染曲库，
   还会让「歌词缺失」这个可行动的信号消失

> 如果最终要开，最低限度要加一条参考实现**没做**的保护：
> **写进文件时在 LRC 头部加一行 `[by:AI 生成，非真实歌词]`** ——
> 这是让「事后翻看也能分辨」的唯一办法。

### 本轮（2026-09-18 深夜）：AI 参与全项目的可行性评估

用户要求「评估 AI 参与整个项目的可行性与哪些功能可以使用 AI」。
产出 **`docs/AI 能力评估.md`**（新增交付物），核心结论：

**AI 的定位是「消歧器」和「补缺器」，不是「生成器」。**

评估框架四条判据（任何一条不过就不做）：
1. **有没有权威来源？** 有的一律不用 AI（歌词/封面/音质/时长都能查到）
2. **错了会怎样？** 只是建议 → 可做；写文件 → 要预览可回滚；**删文件 → 不做**
3. **规则能不能解决？** 能就别调 AI（更快更便宜可复现可测试）
4. **成本/延迟可接受吗？** 成本可忽略（1000 首约 ¥1），**延迟才是约束** →
   所以 AI 只处理「规则失败的那一小部分」

**建议做**：① 搜索匹配消歧（**P0**，AI 只从候选里挑、拿不准返回 null）
② 文件名→元数据批量补全（P1，正则优先 + AI 兜底 + 先预览后写）
③ genre 保留但默认关（P2）④ 歌词翻译（P2，有原文不算编造）

**明确不做**：AI 生成/纠错歌词（编造）、AI 决定查重保留哪一版（删文件，且规则已足够客观）、
自然语言查曲库（**索引里没有年份/BPM，地基不在**）、音源脚本排错（已有方法论）、
「智能选音源」（这是统计问题不是语义问题）。

**现状实测**：AI 目前只接了 **3 个调用点**（`name_parse` / `complete` 透传 / `genre`），
基础设施（配置、静默降级、JSON 契约、按用途用量记账）已够用，加场景基本是「写 prompt + 加 kind」。

> ⚠️ 文档里 §7 诚实标注了**没验证**的部分：成本是估算非实测、

#### ③ ⚠️ 端到端测试挖出真 bug：**封面永远写不进去**

```go
}
```

`tidy.TidyOne` **刻意不下载封面**，要求调用方给字节；而 `Item.CoverBytes` 是 `json:"-"` ——
**HTTP 调用方根本传不进来**。所以封面功能一直是个死结：传 `cover_url` 只会得到一条 Skipped。

而且 `pkg/api/features.go` 里的 `fetchCoverForTidy()` **定义了却从没被调用过** ——
说明当初就是为这件事写的，但没接上。

**修法**：
- 把下载逻辑下沉到 **`security.FetchImage(url, referer)`**（新文件 `pkg/security/image.go`）——
  复用本包已有的 `ValidateURL` / `NewSafeClient` / `LimitedRead`（SSRF 防护），
  并按**魔数**识别 JPEG/PNG/GIF/WebP（不信任 Content-Type）。
- `pkg/api` 的 `fetchCoverForTidy` 改为委托它，并**接进 `HandleTidy`**
  （限并发 4，避免单批 500 首时同时打几百个外网请求）—— 被动接口的封面也一起修好了。
- `pkg/complete` 在 `NeedCover` 时自己下载，填 `CoverBytes` + `CoverMime`。

**修复后实测**（同一个最小 MP3）：

| | 修前 | 修后 |
|---|---|---|
| `cover_filled` | 0 | **1** |
| MP3 体积 | 210 B | **36,649 B** |
| ID3 帧 | TIT2 / USLT | **TIT2 / TPE1 / TALB / USLT / APIC** |

- **只露一行**，其余用 `+N` 药丸收起，展开后按钮变「收起」

#### ① 歌单分享**短链**解析修复（用户报的「解析报错 400」）

**根因**：手机 App「复制链接」给的是短链，`path` 里是**短码不是 id**，
而 `ParsePlaylistLink` 只在链接文本里找数字 id → 必然失败 → 400。
实测三种形态**全部 400**：

| 链接 | 修复前 | 修复后 |
|---|---|---|
| `163cn.tv/abcXYZ`（网易云） | 400「没能找到歌单 id」 | 跟随 302 → 拿到真实地址 |
| `c6.y.qq.com/base/fcgi-bin/u?__=xxx` | 400 | 跟随重定向 |
| `t1.kugou.com/xxx` | 400 | **不重定向**，返回 JSON，从响应体取地址 |

**关键发现**：`163cn.tv` 确实是 302（实测无效短码会跳到 `music.163.com/#404`），
但 **酷狗 `t1.kugou.com` 返回的是 200 + JSON**（`{"status":0,"data":null}`），
**不是重定向** —— 只做重定向跟随会漏掉酷狗。所以两种形态都要处理。

**改法**：`pkg/charts/playlist_link.go` 新增
`ResolvePlaylistLink(raw, client)` —— 先做纯文本解析（零开销），
只在**失败且属于已知短链域**时才发一次出站请求：
① 看重定向后的 URL ② 没重定向就从 JSON 响应体里找第一个 http 链接。
出站走 `security.NewSafeClient`（**逐跳校验重定向目标**，防 SSRF）；
短链域是**白名单**（不把任意用户输入拿去做网络请求）。

**错误信息也改了**：短码失效时返回「分享短链展开后的地址不是歌单页：…（内层原因）」，
用户能一眼看出是链接失效而不是功能坏了。

新增 6 个单测（含「普通链接失败时**不应**发网络请求」这条 —— 防止误伤）。

#### ⑤ 免责声明改为**服务端记忆**（不再每次都弹）

**代码逻辑本来就是对的**（同意后写 localStorage，启动时检查）。
问题在**存储介质**：localStorage 按 origin 隔离，用 IP / 域名 / 换端口访问
就是不同的 origin → 「明明同意过又弹」。

**改法**：改用已有的「窗口记忆」（`services/prefs.js` 的 `loadBool/savePref`）——
它由 prefs 服务同步到应用数据目录 `ui_prefs.json`，**多端共享、清缓存也不丢**。
`ui-prefs` 的键名正则是 `^[A-Za-z0-9_.-]{1,64}$`，`disclaimer_accepted` 直接可用（**零后端改动**）。
键前缀恰好也是 `fn_`，所以老用户已有的 `fn_disclaimer_accepted` **无需迁移**。

启动时本地没有记录会**再向服务端确认一次**（上限 1.5s，后端慢也不卡启动）。

- **实测**：清空 localStorage 后重载，服务端把值同步回来，**弹窗不再出现** ✓
