# v2.24.10 —— 「授权目录」按钮点了没反应

承接用户 m02948「点了,没反应」。上一版（v2.24.9）把桌面入口改成了飞牛统一网关微应用，
网关形态确认生效（静态资源全部 200、`/app/yinshu-ai/api/*` 正常转发），但用户点授权按钮
没有任何反应。本轮把整条链路上的两个「静默失败」都找出来了。

## 根因一：宿主探测判据在飞牛桌面里恒为假

`frontend/src/services/trimHost.js` 原来这样判断「是不是在飞牛宿主里」：

```js
const caps = await withTimeout(app.getHostCapabilities(), 4000, '宿主能力探测')
trimRuntime.value = caps?.runtime || 'unknown'
// hasTrimPicker() = trimProbed && trimRuntime !== 'unknown'
```

而 `getHostCapabilities()` 读的是 `osConnector.config.host`：

```js
getHostCapabilities(){ /* … */ const n = e.osConnector?.config?.host;
  return 'desktop' === n?.runtime ? {runtime:'desktop'} : {runtime: 'web' === n?.runtime ? 'web' : 'unknown'} }
```

真机取证（fnOS 1.2.0903）：
- 门户主包 `/usr/trim/www/assets/index-G02ZKCFw.js` 给 iframe 的 config 是
  `config:{appName, os:{version, theme, language, format}, appMeta}` —— **没有 `host` 字段**；
- 全 `/usr/trim/www`（434 个文件）grep：`host:` 命中 0 次、`sessionCredentials` 命中 0 次。

于是 `runtime` 恒为 `'unknown'` → `hasTrimPicker()` 恒为 false → 所有授权按钮被
`v-if` 藏掉；即使按钮出现了（预览模式），点下去第一步也是
`if (!hasTrimPicker()) return {ok:false, error:'当前不在飞牛宿主环境中'}` —— 立即返回。

但**桥接方法本身是好的**：门户 bundle 里 `pickFile / pickUserFile / pickSharedFile /
authorizeUserFile / authorizeSharedFile / openAppSetting / openFile / openCustomApp /
showFileDetails / setTitle / close / refreshToken / setExitPageTips / getPlatformConfig`
全部存在。

### 改法

判据换成**桥接方法表**：`osConnector.methods.pickSharedFile` 是不是函数。

```js
export function bridgeSupportsPicker(methods, name = 'pickSharedFile') {
  return !!methods && typeof methods[name] === 'function'
}
```

`detectTrimHost()` 改为 `await app.ready()`（SDK 的 `ready()` 就是 `initPromise`，等 penpal
握手完成）后读 `app.osConnector.methods`；握手超时从 4s 放宽到 8s（SDK 自己的 `qe()` 探测就
占 1.5s，加 penpal 往返要余量）。`getHostCapabilities()` 降级为「只写日志的旁证」。

同时把**所有授权按钮改为常驻**（`FnosAuthNotice.vue`、`AppSettings.vue`、`NasDirPicker.vue`），
点击时才探；探测失败把可执行的原话显示出来：

> 当前不在飞牛桌面里（浏览器直接打开时没有系统文件选择器）。请从飞牛桌面的「曲率」图标进入，
> 或到「应用中心 → 曲率 → 设置 → 授权目录」里添加目录。

三个位置在挂载时都会预探一次（`onMounted`），点击时复用结果，不现等握手。

> 旁证：官方应用 `fn-appdownload` 的 `target/www/web-app.js`、`clash-for-fnos` 的
> `index-B21bgMtr.js` 内嵌同一份 `@trimjs/web-app`，都不做 runtime 门控。

## 根因二：`authorized` 把应用自己的数据目录算成「用户已授权」

`config/resource` 里声明了 `data-share: yinshu-ai/data`，系统据此注入
`TRIM_DATA_SHARE_PATHS=/vol1/@appshare/yinshu-ai/data`。那是曲率**自己**的配置/缓存目录，
不是用户授权给它的音乐目录 —— 旧逻辑：

```go
status.FnosRoots = nas.FnOSAuthorizedRoots()   // 含 data-share
status.Authorized = status.SharedCount > 0 || len(status.FnosRoots) > 0
```

真机实测（升级 v2.24.9 后）：

```
GET /api/fnos/auth-status
{"available":true,"api_available":true,"authorized":true,
 "roots":["/vol1/@appshare/yinshu-ai/data"],
 "fnos_roots":["/vol1/@appshare/yinshu-ai/data"],"shared_count":0,...}
```

用户一个音乐目录都没授权，却回 `authorized=true` → 前端提示条
（`shouldPrompt = available && !authorized`）**永远不出现**。而 nginx access.log 显示用户正在
访问 `/vol3/1000/音乐/测试下载`，`/api/nas/browse` 与 `/api/nas/scan` 全部 403 —— 他确实需要
那条引导，但界面上一片空白。这就是「点了没反应」的另一半。

### 改法

新增 `nas.FnOSGrantedRoots()`：管理员共享授权 ∪ `TRIM_DATA_ACCESSIBLE_PATHS`，**剔除**
data-share 声明的自用目录。

```go
func fnosGrantRoots() []string {
	share := map[string]bool{}       // data-share 自己的目录
	for _, p := range fnosDataShareSource() { … }
	roots := fnosSharedRoots()       // 管理员共享授权，全部计入
	for _, p := range fnosEnvRootsSource() {
		if !share[p] { roots = append(roots, p) }
	}
	return roots
}
```

- `authStatus.Authorized = SharedCount > 0 || len(GrantedRoots) > 0`
- `authStatus` 新增 `granted_roots`（仅回环可见），`fnosRoots` 保留原语义（含 data-share，供排障）
- `POST /api/fnos/auth-refresh` 新增 `granted_count`，`authorized` 同口径
- **路径守卫不变**：`AllowedRoots()` 仍包含 data-share，否则曲率写不了自己的数据目录
