## 109 2026-10-08：手机端布局 + 文案瘦身，并且**用真机实测**把结论钉住

用户原话：「优化一下界面，适配手机端，一行可以用两个元素，不一定一行只有一个按钮或者显示。
还有文字介绍太多了。我自己用的，不用太多解释。」（附了两张手机截图）

### 先说这轮最有价值的一件事：能自动验了

手机端布局有个特点：**破了版在开发机上看不出来**（那边没浏览器），而真机上又要靠人眼扫。
这轮补上了 `.dev/measure-mobile.mjs` —— 跑在 NAS 上、用 NAS 本机的 Chrome，
按 390×844 的手机视口把**每个页面**跑一遍，量两件能自动判对错的事：

1. **有没有元素从可见位置向右伸出视口**（横向溢出 —— 手机端最常见的破版）；
2. **两列网格是不是真的排成了两列**（按子元素的 `left` 去重数「列」）。

顺带每页截图（780×1688），人再扫一眼。跑法：

```bash
scp -P 6828 .dev/measure-mobile.mjs liwenyao@192.168.1.66:/tmp/
ssh -p 6828 liwenyao@192.168.1.66 \
  'cd /tmp && /vol1/@appcenter/nodejs_v24/bin/node measure-mobile.mjs http://127.0.0.1:8898/ 390 844 /tmp/shots'
```

⚠️ **两个写这个脚本时踩到的坑**（都会让结果看起来「全绿」或「全红」，都是假的）：

- **手机上顶部导航只有图标、没有文字**（`App.vue` 的 `navDensity` 在 <640px 一律降到 icon 档），
  所以按 `textContent` 找导航按钮会全部 `NOT_FOUND`。改按 **`aria-label`** 找 —— 那个字段
  App.vue 一直设着（无障碍用途），反而是最稳的锚点。
- **滑动切页（SwipePager）把其它视图整条排在左边**（`left` 是负的）。
  第一版没排除它，于是每个页面都报「溢出 8 处」，全是离屏的兄弟页。
  判据改成「`left >= 0` 且 `right > 视口宽`」——**只报从可见位置向右伸出的**。

### 实测抓到的两处真问题（都不是「看起来别扭」，是**真的溢出**）

| 页面 | 症状 | 修法 |
|---|---|---|
| 曲库管家 · 推送 | 「飞牛同步历史」是 5 列 `<table>`，390px 下宽 **596px** —— 「结果」那列整个被推出屏幕 | 改成**卡片行**（flex）：时间与状态在窄屏自动掉到第二行，不再靠横向滚动 |
| 曲库管家 · 下载 | 筛选标签（全部/下载中/…/失败）溢出，**「失败」那一档看不到** | 容器从 `overflow-x-auto` 改成 `flex-wrap`，窄屏折行 |

另外顺手修了一处「一行只有一个」——正是用户说的那个：榜单管理的卡片网格用的是内联
`grid-template-columns: repeat(auto-fill, minmax(196px, 1fr))`，390px 下只剩 **1 列**；
改成 `minmax(150px, 1fr)` 后实测 **2 列**（63 张 + 25 张，容器 322px）。

「自动下载记录」那张 6 列表格这次没数据、量不到溢出，但按同一套判据提前上了
`table-fixed` + 窄屏隐藏「触发」列（与「本地音乐」那张表同一个做法，理由见 NasExplorer 的注释）。

### 布局：手机上「一行两个」是怎么统一的

- **14 处网格**从 `grid-cols-1 gap-N sm:grid-cols-2` 改成 `grid-cols-2 gap-N`：
  手机上默认两列，不再等断点。（`sm:grid-cols-2 lg:grid-cols-3/4` 那几处保留宽屏的更多列。）
- **`PageShell` 手机端收窄**：左右内边距 20px → **12px**、上下 24px → 12px、标题 26px → **19px**。
  390px 的屏上 40px 横向留白等于白扔一成宽度，而这一页要塞的正是两列卡片。

### 文案：用户看不见的那些砍掉了，代码注释一条没动

判据是「**手机上还看得见吗**」：

  「换人接手时知道这页干什么」，手机上是纯占地 —— 而手机恰恰最缺竖向空间。
  一处改动，全站 10 个页面的简介同时收掉。

  `LibraryManager`（18 处，含推送引导、下载四个开关的说明、补全整理、新建订阅）、
  `SourceManager` / `MusicDLSourcePanel` / `SearchView` / `NasExplorer` / `DownloadQueuePanel`，
  以及注入面板 `ui.js` 的「试听音质」提示。
- 顺带修掉 `**粗体**` 写在 HTML 里当字面量显示的问题（`LibraryManager` 的「一首**在线**曲目」这类），
  改成 `<b>`。
- **代码里的注释一条没删** —— 那些是给维护看的（「为什么这么写」），不是用户看的解释。

### 一、版本号策略（已写进 README，并落进长期记忆）

**不要每轮都只加最后一位**，按改动性质选升哪一位：

| 位 | 什么时候升 | 例子 |
|---|---|---|
| 大版本 `x.0.0` | 架构级 / 破坏性变更 | v2.0.0 三容器 → 单容器重构 |
| **中版本 `2.x.0`** | **新增能力**：新功能、新页面、新链路 | **v2.2.0**（洛雪取链、自动下载记录、试听音质阶梯、质量感知的取音池） |
| 小版本 `2.2.x` | 修 bug、UI 微调、文档 | v2.2.1 … |

> 本轮之前我在 2.1.119 → 2.1.124 连加了五个小版本，其中「洛雪取链」「自动下载记录」
> 都是**新能力** —— 按这个规矩它们该走中版本。所以本轮定为 **2.2.0**。

### 二、三条音源的分工（用户口径，写进代码注释）

- **在线（试听）**：网易 + musicdl
- **下载（收藏后后台取音）**：musicdl + lx，**选音质最高的那个**
- **关键授权**：下载**不必最快** —— 所以下载那条腿可以等几十秒

这条授权解决了我上一轮的顾虑。实测确认两条腿的闸是**分开的**，所以「下载慢、试听快」
可以同时成立：

| 路径 | 闸 | 位置 |
|---|---|---|
| 试听 / 发现页搜索 | `onlineSearchWait` **3s**（等各平台）+ `onlineSearchBudget` **8s**（整次） | `pkg/intercept/search.go` |
| 后台下载取音池 | **无闸**，等 searcher 返回 | `pkg/intercept/acquire.go` |

于是把 musicdl 的超时按「下载可以慢」放宽：
sidecar 单源预算 **12s → 120s**、Go 侧整次搜索 **40s → 135s**、池一次要 **5 条 → 3 条**。
试听一点没受影响（它那 3s/8s 的闸在前一层）。

**实测：咪咕现在真的能出结果了**（120s 预算下，`海阔天空` 3 条、耗时 85s）。

### 三、「下载音质不高」的完整根因（每一条都有实测证据）

| # | 结论 | 证据 |
|---|---|---|
| 1 | 下载下来的**全是 mp3** | `/vol3/1000/音乐/测试下载/` 里 8 个文件的魔数全是 `ID3`（扩展名也都是 .mp3） |
| 2 | **取音池恒空** → 每次回落曲目自己平台 | 日志里**一条「换源」都没有**；musicdl 每个源都 15s `unavailable`（12s 预算 vs 实测 49s） |
| 3 | 网易免登录的**硬上限就是 320k mp3** | 实测 `level=lossless` 被静默降级成 `exhigh`（HTTP 200 + 能播的 URL，不报错） |
| 4 | **没登录任何平台账号** | `/vol1/@appdata/yinshu-ai/data/accounts.json` 只有 **2 字节**（`{}`） |
| 5 | 他的洛雪源**不是无损源** | 见下 |

### 四、洛雪这条路的实测真相（这条最要紧）

先说修好的：宿主没打进包（打包 bug）、缺省关、结果不带音质、池里没有解析器、
脚本从没落盘、node 不在应用 PATH 里 —— 六处全修了，**宿主现在真的起来了**
（`/health` 能看到 5 个脚本加载成功）。

但把宿主跑起来之后，测出来的结论是：

```
同一个 wy id（354233 晴天），5 个脚本 × {flac, 320k} —— 10 次调用返回的是**同一个 URL**：
  http://music.nxinxz.com/wy.php?id=354233&level=standard&type=mp3
```

- **5 个脚本是同一个聚合站（`music.nxinxz.com`）的马甲**；
- 那个上游**无视档位参数**：我要 `flac`、要 `320k`，它都回 `level=standard&type=mp3`；
- 脚本 `inited` 里声明的 `qualitys: […,"flac","flac24bit"]` **只是宣称**，handler 不认。

**推论（重要）**：如果把洛雪接进下载池当「更高音质」，**会把 320k 降成 128k** ——
所以这一条**故意不接**。防线在池的「严格更好」那道筛上：洛雪候选拿不到真实档位
（他的脚本既搜不了、也不给 `_types`），档位恒为空 → 算最低档 → 永远不会被选中。
这条不是「没做完」，是**验完之后的正确结论**。

### 五、所以「音质不高」不是曲率的 bug，是源的能力上限

现有三条源的实际能力：

| 源 | 能给什么 | 结论 |
|---|---|---|
| 网易（免登录） | **真实完整的 320k mp3** | 天花板 |
| musicdl 咪咕 | **mp3**（`ext=mp3` → 池里按 320k 计） | 能用了，但仍是有损 |
| 他的 5 个洛雪脚本 | **standard mp3**（上游无视档位） | 不是无损源 |

**要真无损，只有三条路**（都需要用户决定，不是我能自己选的）：

1. **登录网易云 VIP**（扫码）→ 我把登录 cookie 接进解析器 → 走 VIP 无损。
   参考实现（fnmusic-ext 的 musicbox 源）走的就是这条。**这是最现实的一条**；
2. 换一个**上游真的给 flac** 的洛雪源（现在的 5 个都指向同一个不给 flac 的聚合站）；
3. 接受 320k mp3。

### 六、本轮顺手修掉的（都有测试或实测）

- **打包**：`lx_host/server.mjs` 从来没被复制进包（`REF_INNER` 声明了、复制代码漏了）；
  **并且结构自检只打印「缺少：…」不加进 errors** —— 所以构建照样报「自检通过」。
  两处都修了：先只加严断言 → 构建**当场失败**并指出缺 `sidecar/lx_host`（证明断言有效），
  再补上复制 → 通过。用例 `TestSyncScripts*` / `TestResolveNodeBin*`。
- **node 可执行文件**：飞牛上 node 装在 `/vol1/@appcenter/nodejs_v24/bin/node`，
  **不在应用的 PATH 里**，而原来只做 `exec.LookPath("node")` → 宿主根本起不来，且失败静默。
  新增 `resolveNodeBin`（绝对路径 → `QULV_NODE_BIN` → PATH → 已知安装位置）。
- **洛雪脚本落盘**：用户脚本正文存在配置里，而宿主要读 `<Dir>/*.js` —— 中间没有桥，
  目录永远为空。新增 `lxnode.SyncScripts`（同步语义 + 文件名防穿越）。
- **洛雪取链那一半**：池里没有 `lx:<src>` 解析器（测试里那句注释写着「生产侧由 lxnode 注册」，
  而生产侧从来没注册过）。新增 `lxresolve.go`：按脚本自己声明的最高档去要直链。
- **`flac24bit` / `hires` 在池里算最低档**（掉进 default → 0）→ 归进无损档。
- **洛雪结果不带音质**：宿主没读 LX 契约的 `_types` → 现在读了。
- **手机端**：三处网格改回**整行**（用户：「有些就是需要一行一个，卡片内的元素需要完整，
  比如音源卡片等」）—— 音源卡片、榜单卡片、AI 表单；其余保持两列。
