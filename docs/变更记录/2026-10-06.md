## 100 2026-10-06：tee 补标签后同步登记表大小 → **v2.1.114**

> 承接 turn 98 的 tee 全链路复验 —— 那次注意到一处对不上：登记表写的是**流下来的**字节数，磁盘上是**补完标签之后**的大小。

### 问题

`finishTee` 是先 `Put`（登记流下来的大小）再 `enrichAfterTee`（补标签、文件变大）—— 于是登记表永远差那几十 KB。真机实测（turn 98）：流下来 `10,878,476`、落盘 `11,029,926`。

**「登记说 A、磁盘上 B」这种对不上，排查时会让人以为是别的问题**（比如怀疑文件被截断或写坏）—— 而它其实只是「标签还没写进去时记的账」。

### 改动（`backend/pkg/intercept/tee.go`）

补标签**成功之后** `os.Stat` 一次，大小变了就再 `Put` 一遍（`Put` 是幂等的）；补标签**失败时不更新** —— 文件没变，原来的大小就是对的。

### 测试与变异

`backend/pkg/intercept/tee_test.go` 的 `TestTeeEnrichesTagsAfterPromotion`：假补标签后端现在会**真的往文件里追加字节**（模拟写标签 —— 否则这条根本测不到），并断言登记大小 == 落盘真实大小。

### ⚠️ 一次**误报**的排查（教训比结论值钱）

真机验收时 `POST /music/api/v1/playlist/add-track` 带回 `{"code":100002,"msg":"invalid arguments"}`，我一度判定「拦截层认不出在线 guid、请求被透传给官方」（官方对**它库里没有**的 track guid 就回 100002，见参考实现 `/tmp/fnme-z/proxy/app.py:7501`）。

于是补了两版排查日志（v2.1.105/106），最后一条把顶层键和原始 body 一起打出来 —— 结果直接指向真相：

```
歌单加曲：0 个 guid 里一个在线曲目都没认出（官方 0 个），透传给官方；playlist="d06d45…" guids=[]
```

`playlist` 取到了、`guids` 是空的。**原因在我的验收脚本**：`page.evaluate(fn, a, b)` 只传**第一个**参数，所以 `trackGUIDs: [g]` 里的 `g` 是 `undefined` → `JSON.stringify` 成 `[null]` → `asString(null)` 是空串 → 被跳过 → `guids=[]`。改成传一个预先拼好的 body 字符串，一次就通。

**结论：拦截层没有 bug。** 三个教训：

1. **别拿被我们拦截过的端点当对照组的取样来源** —— 我最初用 `/music/api/v1/track/list` 的第一条当「官方曲目」，但那个端点**正是我们自己接管并合并在线结果的**，取出来的还是虚拟 guid，所以「官方曲目也失败」根本不能证明请求形状有问题。
2. **`page.evaluate` 只传第一个参数** —— 多参数会静默变 `undefined`，表现是「服务端收到了请求但字段是空的」，看起来极像服务端的 bug。
3. **`guids=[]` 有两种截然不同的原因**（字段名对不上 / body 压根没解析出来），只看 `guids=[]` 分不清 —— 所以 v2.1.106 把顶层键 + `rawLen` + 原始 body 一起打出来。**日志里能一次分清的事，不该靠猜两轮。**

### ① 同档比体积（v2.1.99）

你最初的指令是「挑最高音质（**无损优先、同档比体积**）」。v2.1.93 只做了前半句：档位高的赢，同档位之间保持原顺序 —— 体积根本没参与比较。

根因是**链路断点**：外挂音源其实**一直在报**文件体积（`sidecar/musicdl_service/core.py:252` 的 `"file_size": int(getattr(song, "file_size_bytes", 0) or 0)`），但 Go 侧 `search.UnifiedSong` 没有对应字段，映射时被静默丢掉了。

改动：`UnifiedSong` 加 `FileSize`；`unifiedFromMusicDL` 带过来；`pickBestQuality` 改用新的 `betterCandidate(b, best)`：

- 档位不同 → 档位高的赢；
- 档位相同 → **体积大的赢**（同一首歌、同一档位，文件更大 = 码率更高）；
- 体积**未知**（0）的一方**不主动占优** —— 它是「平台没给这个字段」，不是「更小」。外挂音源里缺这个字段是常态，把 0 当体积会让「没给字段的源」永远选不上。

测试 +2（`TestPickBestQualityComparesSizeWithinTier`、`pkg/search/musicdl_size_test.go`），**变异 4/4 全杀**。真机确认搜索响应里已经带上了体积：`{'n': '晴天', 'src': 'mg', 'q': '320k', 'size': 10792962}`。

### ② 修「音源全关掉还在搜」（v2.1.100）

验收要求里有一条「音源页逐个启停生效」。真机上一试：在音源管理页把源**全关掉**，再搜同一个平台 —— **照样出结果**。

根因是 `MusicDLActiveSources()` 用 `len == 0` 判断「没配过」，把两种不同的意图混成了一种：

| 值 | 含义 | 该怎样 |
|---|---|---|
| `nil` | 老配置 / 新装，从没配过 | 用默认源（mg）✅ |
| `[]` | 用户在音源页把源**全关掉** | 一个都不搜 ❌ 旧代码也当成「没配过」 |

修法两处：

1. **判 `== nil` 而不是 `len == 0`**。
2. **`musicdl_sources` 去掉 `omitempty`** —— 否则「全关」序列化时被省成缺字段，重启后读回来是 `nil`，又悄悄变回默认源（用户会以为设置自己跑回去了）。

想整个关掉 musicdl 请用**总开关** `musicdl_enabled`；清空名单只表示「一个外挂平台都不搜」。两者是不同的意图。

新增 3 条用例（含「全关要活过重启」的 JSON 往返 + 走一遍 ConfigManager 的持久化）；一个**编码了旧错误行为的**老用例（`TestUpdateEmptySourcesFallsBackToDefault`，注释还写着「空切片 = 回到默认…在语义上等价」）改写成正确行为。**变异 2/2 全杀**。

## 86 2026-10-06：修 tee 提升文件没标签的洞（新增「只补标签」路径）→ **v2.1.97**

> 修上一轮（v2.1.95）自己记下的缺口。

### 问题

`边听边下`（tee）是直接复制流字节、**没走下载接口** —— 所以提升出来的文件标题/歌手/专辑/封面/歌词**全是空的**。歌能听、能绑定，但在飞牛里元数据是空的（只有文件名带着信息）。这跟「边听边下」本该达到的效果不符。

### 修法（不是重新下载）

重新下载一遍会把 tee 省下的带宽又花回去。所以新增一条**只补标签、不重下音频**的路径：

| 文件 | 作用 |
|---|---|
| `backend/pkg/downloader/downloader.go` | `EnrichExisting(song, path)` + `HandleEnrichExisting`：给**已经存在**的文件补标签 |
| `backend/pkg/api/routes.go`、`catalog.go` | 注册 `POST /api/download/enrich`（接口目录里也补了 `/api/download/song` 的 `embed_cover` 字段） |
| `backend/pkg/intercept/tee.go` | `enrichAfterTee()`：提升成功后调它一次，带上曲目元数据 + 下载偏好 |

**路径守卫**：这个接口会**写盘**，而 `path` 来自调用方 —— 只允许改下载目录里的文件（`..` 穿越也挡）。不做检查它就是一个「往任意路径写标签」的入口。

**失败只记日志**：文件已经在库里、已经能听，补标签是锦上添花 —— 不能因为抓不到封面就把一首已经下好的歌算成失败。

### 测试与变异

- `backend/pkg/downloader/enrich_test.go`（新）3 条：**目录外路径必须拒绝** + `..` 穿越必须拒绝 / 空路径 + 不存在的文件 + 空文件（失败下载的残骸）都要拒绝 / 目录内的真文件必须**放行**（否则 tee 补标签永远不生效）。
- `backend/pkg/intercept/tee_test.go` +2：提升后**必须**调 `/api/download/enrich` 且载荷带 path/歌名/歌手/歌词偏好 / 没接本机 API 时不崩且仍完成提升。
- **变异 6/6 全杀并逐字节还原**。

⚠️ 写这一轮时踩到一个小坑：守卫最初判的是 `i.cfg.LocalAPI`，而真正发请求的 `postLocalAPI` 用的是构造时解析出来的 `i.localAPI` —— 判错了会在测试环境里**静默不补标签**，用例先抓出来了。

## 84 2026-10-06：④ 边听边下（tee）→ **v2.1.95**

### 两条硬规矩

1. **播放优先**：先写给客户端、再写盘；盘写失败就把文件句柄丢掉继续播。tee 是搭便车的，不是主角 —— 绝不能因为磁盘问题变成「听不了」。
2. **只提升完整文件**：半截文件进了曲库比没有更糟（它会一直播到一半停，而用户以为已经下好了）。必须「拿到的字节数 == 上游声明的总长」才提升；未完成的**删掉**。

### 什么时候不 tee（每一种都有理由）

开关关着 · 已经在库里（别再存一份）· 上游回 **206 分片** · 客户端要的是**中段 Range**（拖动/续传拼不成完整文件）· 上游没给 `Content-Length`（判断不了完整，宁可不存）· `HEAD` 请求 · 没有下载目录。

## 80 2026-10-06：让咪咕的歌真的能在飞牛里搜到、能播 → **v2.1.86 / 87 / 88**

> 承接 79（v2.1.85 把外挂平台接进了搜索）。那一版装到真机上一验就发现不对，**连着两层 bug**，最后靠实测数据收敛默认值才真正可用。三个版本是一次连续排查。

### 第一层（v2.1.86）：合并「等所有平台」，8 秒预算形同虚设

真机现象：飞牛里搜一首歌要等二十多秒，而且**一首在线歌都不出**。日志：
`[MUSICDL] 搜索源 bq 当前不可用：源 bq 超过 25s 预算`。

根因：拦截层的合并是 `wg.Wait()` —— **等每个平台都返回**。而 `i.searcher` 是同步的、没有 context，那个 8 秒总预算**根本没起作用**：只要有一个平台慢，整次搜索就跟着慢。

修：改成**限时等待**（`select { <-done; <-time.After(...) }`），到点只用已经回来的平台；慢的那个这次不出结果。同时把 sidecar 的单源预算 25 → 12 秒。

### 第二层（v2.1.87）：解析用了一个**已经过期的 context**

v2.1.86 装上去：搜索 8 秒返回了，但**在线歌还是 0 首**。日志：

## 77 2026-10-06：musicdl 外挂音源 —— 在线平台从 2 个扩到 5 个 → **v2.1.83**

> 看板卡 `6b471228`。用户问「musicdl 弄了吗」时还是 `executionCount: 0`；这一轮把它做完。

### 为什么是「外挂进程」而不是原生 Go

酷狗 / 酷我 原生**搜得到、拿不到直链**（`err_code 30020` / `The request is illegal!`）—— 那不是写得不认真，是风控。咪咕 / 千千 / B站 更是完全没有。musicdl 覆盖十几家音源，靠的是**跟着各平台改**的一套爬取逻辑（还带 `curl_cffi` 做 TLS 指纹伪装）；在 Go 里复刻等于长期维护十几个随时会失效的解析器。

所以分工：**原生的（wy / tx）继续原生**（快、稳、无外部依赖），剩下的交给一个 Python sidecar。对 `Pool` 来说两者没有区别 —— 都是 `Resolver`。

### 平台短码映射（写死，不靠字符串推导）

| musicdl 源 | 曲率短码 | 原生情况 |
|---|---|---|
| `NeteaseMusicClient` | `wy` | 搜索 ✓ 直链 ✓（走 sidecar 纯重复 → 默认关） |
| `QQMusicClient` | `tx` | 搜索 ✓ 直链 ✓（同上） |
| `KuGouMusicClient` | `kg` | 搜索 ✓ **直链 ✗** |
| `KuwoMusicClient` | `kw` | 搜索 ✓ **直链 ✗** |
| `MiguMusicClient` | `mg` | 都没有 |
| `QianqianMusicClient` | `bq` | 都没有 |
| `BilibiliMusicClient` | `bi` | 都没有 |

**默认启用 `mg,bq,bi`**（纯增量）。`kg` / `kw` **默认关**：它们原生能用只是放不出声，接了 sidecar 之后**搜索与解析都会换成 musicdl**（一个平台只能有一个 id 空间，一半原生一半外挂就是「搜得到、点开放不出」），属于**改变现有行为**，该由用户自己决定。

### 两个关键设计决定

**① resolve 是无状态的。** musicdl 的直链是**搜索结果对象上的字段**（`download_url`），不是「拿 id 去问」能拿到的。参考实现（`/tmp/fnme2/musicdl-service/app.py`）的做法是 sidecar 自己长期缓存搜索结果、之后按 id 反查 —— 代价是**进程一重启，所有已入库曲目全部解析失败**（它给调用方返回「缓存过期了，请重新搜索」，而曲率的曲目是存在 NAS 库里的，那些 id 不会因为 sidecar 重启就失效）。这里改成**带歌名 + 歌手回搜**再按 `id → 歌名+歌手 → 歌名` 三级匹配，进程内缓存只当加速用。为此在 Go 侧加了**可选扩展** `QueryResolver`（原生 wy/tx 不实现 → 两个既有实现与它们的用例一行没改）。

**② sidecar 掉线时曲率照常工作，且网络故障绝不写负缓存。** 写了负缓存等于把那首歌锁死五分钟不可播，sidecar 恢复了也没用 —— 专门有用例守这条（`TestSidecarDownDegradesWithoutPoisoningCache` / `TestSidecarErrorStatusDoesNotPoisonCache`）。只有「sidecar 明确说这条没有直链」才负缓存。

## 76 2026-10-06：真机抓到的 bug —— 正在播放时「下载到曲率」是灰的 → **v2.1.82**

> 承接 75。v2.1.81 装到飞牛上验收时，面板里歌名 / 歌手 / 封面全对，唯独 `下载到曲率` 点不动（品牌色**软底**样式 = `disabled`）。这一轮就是查它。

### 取证：先在页面里旁听它自己的请求

第一条路（读官方 `music.db` 拿 token 再 curl 官方接口）走不通：`select user_token from user limit 1` → `sqlite3.OperationalError: no such column: user_token`（表/列名不对，**没继续猜**）。

改成第二条路 —— **在页面里旁听它自己的请求**（页面自带凭据，不必自造 token）：注入 XHR + `fetch` 记录器（`window.__probe`）→ 点「首页」再点「热歌榜」→ 扫全部响应找那个 guid。读到的：

| 响应 | 该 guid 出现次数 | 附近有 `is_online` |
|---|---|---|
| `playlist/list` | 2（都是 playlist 对象的 `coverId`） | 0 |
| `playlist/detail?guid=online:playlist:chart:wy_3778678` | 1（同上，playlist 的 `coverId`） | 0 |
| `track/playlist-detail/list` | 6 | **6**（首个 track `is_online: true`、`source: "wy"`） |
| `track/metadata?guid=…` | **16** | **只有 5** |

关键在最后一行：`track/metadata` 的响应体（2070 B）里，**精确等于该 guid 的节点有两个** ——

- 顶层那个：`…"guid":"784017f9…","isFavorite":false,"is_online":true,"name":"海屿你","source":"wy"…`（曲率造的）；
- 嵌在 `"track":{…}` 里的那个：键按**字母序**（`accessStatus/album/artists/audioSpec/…`）→ 这是**官方上游原样透传**的那份，**没有 `is_online`**。

### 根因

`assets/ui.js` 的 `harvest` 是**最后写入者赢**：遍历到嵌套的上游 track 对象时，把 `index[guid].online` 从 `true` 覆盖成 `false`（`isTruthy(undefined)` = false）。于是「本地曲目不显示下载」这条规则反过来把在线曲目也挡掉了。

实测证据（同一表达式，前后对比）：起播前 `__QULV_UI_TEST__.indexOf(guid).online === true`；起播（触发 `track/metadata`）后变 **false**。

> 顺带确认：`is_online` 这个字段在**官方前端 bundle 里出现 0 次**（官方不读它），Go 侧两个 VO（`pkg/online/vo.go:150` 的 MetadataVO/SearchVO、`vo.go:202` 的 FavoriteVO）**都**正确地设了 `"is_online": true` —— 问题纯粹在客户端**怎么合并**多份说法。

### 修复：只升不降

新增 `mergeRecord(prev, node)`：

- `is_online` 为真 = 权威的「在线」；
- **字段缺失**只说明「这个响应没说」，**不能**拿来否定已知事实；
- 只有**显式**为假才降级；
- 标题 / 歌手 / 来源同理：新记录里为空就保留旧的，别用空串盖掉好数据。

### 测试

`frontend/src/engine/pageUi.test.mjs` 加 2 条（共 **13** 条）：① 先 harvest 一份带 `is_online: true` 的，再 harvest 一份**没有**该字段的（模拟上游透传），断言仍为在线、且 `source` / `artists` 不被空值盖掉，最后显式 `false` 才降级；② `mergeRecord` 的纯函数语义（缺字段保旧 / 显式假降级 / 显式真升格 / 首次见到且无字段 → 保守算本地 / 带值用新值）。

⚠️ 写这条用例时踩了个坑：**不能用 `assert.deepEqual` 比 `mergeRecord` 的返回值** —— 它在 `node:vm` 沙箱那个 realm 里跑，返回对象的原型与测试 realm 的不是同一个，`deepEqual` 会因为原型不同而红。改成逐字段比。

**变异校验 2/2 全杀并逐字节还原**：把合并策略改回「最后写入者赢」（用例 6、7 红）；让标题/歌手/来源直接覆盖（同样红）。

## 73 2026-10-06：在飞牛音乐页面里直接下载在线曲目 —— 页面注入框架 + 「下载到曲率」菜单项 → **v2.1.79**

它同时是 `1ceb1ccf`（曲率 ↔ 飞牛双向切换按钮）要复用的那一套。

### 先侦察：官方页面长什么样

官方音乐页是 React + **Semi Design**，曲目列表**虚拟滚动**（`react-window`，每行挂在一个
`div[data-index]` 的绝对定位盒子下，滚动时复用节点）。行右侧 `更多操作` 按钮的 `aria-label` 是常量，
点开是一个 `role=menu` 的 `.semi-dropdown-menu`，条目就是 `.semi-dropdown-item`
（播放 / 下一首播放 / 加入播放列表 / 收藏 / 添加到歌单 / 查看专辑 / 查看歌手 / 从歌单移除 / 歌曲信息）。

**关键发现**：官方给在线曲目返回的 `coverId` **就是 `guid`**（抽样 8/8 命中）——
也就是说行 DOM 里的 `img[src*="coverId="]` 直接就是那只曲目的虚拟 id，
不需要为了「这一行是谁」另开一个接口。

### 三条架构决定

1. **注入点在转发层，不在 API 层。** `handlePageShell` 只对 `GET` + `Accept` 含 `text/html`
   的请求动手：缓冲文档、在 `</body>` 前插一行 `<script defer src="/music/_qulv/ui.js?v=…">`。
   其余一切（静态资源、接口、下载、WebSocket 升级）**一律不认领**，原样交给接管层的反向代理。
   代价是没有 SPA 路由感知；收益是官方页面的可用性没有被押在几行字符串拼接上。
2. **必须丢掉条件请求头。** 注入前先 `Del("If-None-Match")` / `Del("If-Modified-Since")`；
   注入后重算 `Content-Length`、丢掉 `ETag`/`Last-Modified`。少任一条，真机上就会出现
   「升级了但界面没变」（浏览器拿 304 用旧缓存，或按旧长度截断把脚本切掉）——
   这类问题在现场最难查，宁可每次多传 10 KB 文档。文档超过 1 MiB 则**不注入、直接流式转发**。
3. **通道前缀从裸 `/_qulv` 挪到 `/music/_qulv`（修真 bug）。** fnOS 的 nginx 里只有
   `location /music` 指向入口 socket，裸的 `/_qulv/` 那棵树归一管的 livez/healthz。

### 六条口径（两条是故意的「不抄」）

1. **榜单目录不抄它的常量表。** 它写死 20 个酷狗榜 + 18 个网易云榜（101 个 → 实际 38 个 id 常量），

   直接用 → 候选 **wy 63 + tx 25 = 88 个**，且平台自己上下架榜单时不用改代码。
2. **只放有直链解析器的平台。** `pkg/online` 只实现了 `NetEaseResolver` 与 `QQResolver`
   → kg/kw 的榜单挂上去就是「点开能看、点了不出声」。白名单 `vChartPlatforms = {wy, tx}`。
3. **曲目来源走本机回环** `GET /api/charts/detail?source=&id=`。四平台的详情抓取函数都是

   那是重写几百行解析代码的风险；回环成本只是一次本机请求（`pkg/api/routes.go:91-93` 三个
   charts 接口都没有鉴权中间件）。
4. **榜单曲目同样过 `playableOnly()`。** 口径与虚拟歌单一致：**进列表的每一首都必须能播**。
   代价是 QQ 榜单的长度会明显短于真实榜单（300 首里能播的没那么多），这是有意的取舍。
   注意顺序：**先按 `vChartSize = 100` 截断，再 `Normalized()`，再 `playableOnly`** ——
   把 300 首全丢给解析器既慢又没必要。

   显式 true、显式 false（新装用户不必先去界面点一下才能用；显式关掉的人重启后仍是关的）。

### 归因

### 修复：`frontend/src/engine/lx-runtime.js` 三道闸

原则：**第三方脚本不该拿走主线程，也不该拿走诊断能力。**

1. **定时器闸门** —— 脚本作用域里的 `setInterval` / `requestAnimationFrame` 默认**不调度**
   （返回数字句柄，`clearInterval(0)` 无害）；`setTimeout` **照常放行**
   （一次性定时器有界，且我们自己的调用超时就走它，一刀切会掐掉正常音源的两段式注册）。
   放行开关：`window.__LX_ALLOW_SCRIPT_TIMERS__ = true` 或 `localStorage['lx.allowScriptTimers'] = '1'`。
2. **求值期换全局** —— 有的混淆器写死 `window.setInterval(...)`，所以求值那一小段窗口里
   把 `globalThis.setInterval` / `requestAnimationFrame` 也换成闸门，`finally` 还原。
   ⚠️ 真实实现必须 `const realSetInterval = globalThis.setInterval` **先抓在手里**，
   否则全局替换后自我调用直接爆栈。**故意不换 `setTimeout`**。
3. **`console` 抢回** —— 见下。

### 顺带挖出的第二件事：那条脚本把控制台整个换掉了

修完之后日志停在「Loading script: custom_43604870581e3782」后再无输出，
既没有 `Loaded OK` 也没有 `Load error`，**看起来像脚本同步死循环卡死**。

真相是 **它把 `console.log` / `info` / `warn` / `error` / `trace` 全换成了自己的函数**，
之后的**所有**日志静默消失 —— 连它自己的报错都看不到。
排除过程：① `XMLHttpRequest.prototype.open` 探针显示 6 条音源的脚本**全都请求到了**
（149 → 868ms，循环没断）；② 比对函数引用才发现 `console.log !== 我们装的那个`。

所以加了 `reclaimConsole(sourceId)`：每次加载完逐项比对并抢回，且喊一声是哪个音源干的。实测日志：

```
[LX-RUNTIME] 音源 custom_43604870581e3782 改写了 console.log / console.info / console.warn /
console.error / console.trace，已抢回：脚本劫持控制台会让所有日志（含它自己的报错）静默消失，
诊断能力不能交给第三方。
```

⚠️ 抢回发生在求值**之后**，那条脚本求值期自己打的日志仍然会丢。这是刻意取舍：
若在求值前就把 `console` 冻结成只读，带 `'use strict'` 的脚本会直接抛错、音源加载失败 ——
那比丢几条日志严重得多。

**教训**：「日志突然停了」不等于「卡死」。先验「日志通道本身还在不在」。

## 70 2026-10-06：同源通道 —— 注入到飞牛音乐页面的脚本，有了安全的回程 → **v2.1.74**

看板卡 `b6fa812b`（在飞牛页面内直接下载在线曲目）的**后端那一半**。

**为什么必须同源**：官方音乐页面的 origin 是 NAS 本身，而曲率后端在 `:8898` —— 直连是跨域。
放开 CORS 的代价是把「能下载、能整理、能读整机文件」的一整套能力暴露给任意站点。
走同源之后，注入脚本用相对路径即可，且**没有预检请求**。

新建 `backend/pkg/intercept/qulvbridge.go`：`qulvPrefix = "/_qulv"`、`qulvAPIPrefix = "/_qulv/api"`。

| 路径 | 作用 |
|---|---|
| `POST /_qulv/api/download/online` | 入参只有一个虚拟 guid（32 位 hex）。直链由**后端**解析，落盘复用既有的 `/api/download/song`（标签、封面、去重都在那儿） |
| `/_qulv/` 下**其它一切** | 一律 404，**且不转发给官方** |

三条设计约束：

- **绝不猜 guid** —— 只认本应用登记表里的 id；不在表里就 404（「该 id 不是本应用发出去的，
  或登记表已被回收」）。猜错会把不相干的歌写进用户曲库。
- **不可播放要说清原因** —— 502 且区分 `ErrNotPlayable`（收费 / 无版权 / 地区限制）
  与 `ErrNoResolver`（该平台没有可用直链解析器），不是笼统的失败。
- **兜底 404 不转发官方** —— 官方对未知路径走 SPA fallback 返回 `200 + HTML`，比 404 难查得多。

新增 `backend/pkg/intercept/qulvbridge_test.go` 六条，含白名单用例

五条路径全 404 且不碰官方）。**证明有效**：去掉兜底路由后该用例立刻报四条路径「应被兜底路由处理」。
