## 108 2026-10-07：① 修「在线听过的歌不出现在最近播放」——根因是**夹具照想象的形状摆的**

用户原话：「增加在线听过的歌也出现在官方『最近播放』里」。查证结论：**这条链路从上线起一次都没生效过**。

### 真机取证（先证明它真的坏了）

- `/api/logs` 的环形缓冲里 `[INTERCEPT]` 有 138 条（虚拟歌单、取流、换源都在跑），
  **没有一条**跟播放历史有关；
- `GET /api/nas/read?path=/vol1/@appdata/yinshu-ai/data/online/downloaded.json` → 有内容（自动下载是活的）；
- 同一目录下的 `play_history/fp-485d391520ecf02c.json` → **404**（路径不存在）。

即：同一批代码里，别的链路活着、只有写播放历史这条死了。**不是偶发，是从来没写进去过。**

### 根因：上报体的形状

`handleEventReport` 以前只认**扁平体**：`{"eventType":"track_play","trackGUID":"…"}`。
而真机前端根本不是这么发的 —— 从 NAS 上官方页面的 bundle 里读到的构造代码是：

```js
Cb = e => ({ eventType: Bi.TrackPlay, occurredAt: e.startedAt,
             payload: { trackGUID: e.trackId } })
wb = e => ({ events: [Cb(e)] })
```

**事件装在 `events` 数组里、guid 藏在 `payload` 里**。同一个 bundle 的枚举把取值钉死了：
`e.TrackPlay=\`track_play\`` —— 所以 `eventTypeIsPlay` 的判据本身没错，错的只是**取字段的位置**。
`firstString(body, "eventType", …)` 在顶层找不到，于是每一条播放上报都被判成「非播放事件」原样透传，
一条都没记。

这正是 `HANDOVER.md` §4.x 点名的那个坑：**测试夹具按实现的想象摆**。旧用例
（`TestEventReportRecordsPlay`）用的就是扁平体，它一直是绿的 —— 因为它和实现一起错。

### 改法

`parsePlayEvents` 两种形态都认（嵌套体是**真身**，扁平体只是**兼容**）：

- 逐条读 `events[]`，事件层与 `payload` 层都收 guid；
- 顺带认页面卸载时 `navigator.sendBeacon` 的补发（同一个形状，走同一个端点）；
- `occurredAt` 是**毫秒**，换算成秒后当 `PlayedAt` —— 补发可能比事件本身晚到很久，
  用「收到时间」会把刚听完的那首排到列表更靠后；
- 一条在线曲目都没认出来 → 原样透传（本地曲目的播放统计照旧归官方）。

### 验证

- 新增 3 条用例：嵌套体记账并采信 `occurredAt`、`payload` 缺 guid 时既不误记也不吞请求、
  嵌套体里的非播放事件（`lyric_offset_change`）原样透传；
- 旧的扁平体用例**保留**（兼容形态，不能因为修了真身就把老客户端踢掉）；
- 后端 33 包全绿。

## 108 2026-10-07：③ 试听音质阶梯 + 飞牛页面里的显示与切换

用户两问：「飞牛音乐页面在线播放的时候，播放音质用的哪个源，可以有切换的按钮吗？」
「增加音质阶梯：试听音质按 flac → 320k → 128k 逐级递减，能上无损就上无损。」

### 先摸清平台能力（真机实测，不是照文档猜）

派了一个子任务逐档实测两个平台的**免登录**接口，结论写进了 `pkg/online/tier.go` 与 `netease.go`：

| 平台 | 免登录能拿到什么 | 关键坑 |
|---|---|---|
| 网易云 | **真实、完整的 320k mp3**（`exhigh`） | 请求 `level=lossless` 会**静默降级**成 `exhigh`：HTTP 200、code 200、一个能播的 URL，**不报错也不给 null**。不回读 `level` 就会把 320k 当无损报给用户 |
| QQ 音乐 | 约 **48 秒 / 128k 的试听片段** | 档位由 vkey 请求里的 `filename` 前缀决定（F000 flac / M500 320k / C400 128k）；未登录问 flac 恒 `result=104003`；**一条 songmid 只能配一个 filename**，塞多个会把整条请求毒掉（101404） |

顺带修正了一处长期存在的误读：`/api/song/enhance/player/url/v1` **必须带 `encodeType`**
（值无所谓），不带时接口返回一个**重复了两遍**的 `{"msg":"参数错误","code":400}` —— 看起来像被限流，
其实只是少了个参数。

### 改法

- `pkg/online/tier.go`（新）：档位常量、`TierRank`、`PlaybackLadder = [flac, 320k, 128k]`、
  `TierResolver`（**可选接口**，与既有的 `QueryResolver` 同一个套路：不实现就退化成问一次 `Resolve`）；
- `Resolved.Tier` 是**实际拿到**的档位（不是请求的档位）；`Pool.ResolveTier` / `ResolveLadder`
  带档位缓存键；负缓存从「一个布尔」改成**存错误本身** —— 阶梯要靠它区分
  「降一档继续」（`ErrTierUnavailable`）与「这首歌别试了」（`ErrNotPlayable`）；
- `playback_quality` 配置键：`auto`（默认，本平台内阶梯）/ `lossless`（无损优先，本平台拿不到
  无损时去**下载源池**找同名无损版）/ `320k` / `128k`（固定档位，不降级）；
- 注入面板（`assets/ui.js`）新增「试听音质」一节：档位胶囊由**后端给清单**
  （`/api/info` 的 `quality_options`），界面不写死；「正在播放」下面多一行
  「取音 网易云 · 320K」—— 这两个事实**只有后端知道**（档位是解析时回读的、源可能被换过），
  所以走同源通道 `/music/_qulv/api/now` 异步取，取不到就整行隐藏，不显示猜测值。

**默认为什么是 `auto` 而不是 `lossless`**：试听的首字节延迟是用户直接感受得到的，
为了「可能存在的无损」每次首播都多等一轮跨源搜索不划算。要真无损就明确切「无损优先」——
这是一个用户可以自己权衡的选择，不该由我们代选。

## 108 2026-10-07：④ 榜单管理的「音质下载」+ 自动下载记录

用户：「榜单管理增加音质下载选项，专门针对在飞牛音乐页面中，收藏或者下载时，下载的音质，
并且将下载记录展示在任务状态，该任务可以单独增加页面（比如自动下载记录等标题）。」

### 为什么必须新增一张后端表

网页端的下载队列（`services/downloadManager.js`）记的是「用户**在曲率这个页面上**排队下的那些」。
而收藏 / 加歌单触发的下载发生在**飞牛官方页面**上，曲率前端根本不知道它存在 ——
用户点完红心，歌在后台下来了，队列里却一行都没有。**这正是用户报的现象**。

所以新增 `pkg/online/autolog.go`：追加写、有上限（500 条）、成功与失败**都记**
（排障要看的恰恰是失败那几次，而失败根本不会进 `downloaded.json`）。
与 `downloaded.json` 的分工写在该文件顶部：一个记「哪些已落本地」（一 guid 一行、覆盖写），
一个记「每一次动作」。

记录 id 是「时间戳 + 序号 + 内容哈希前 8 位」—— 同一秒里连着下三首同名歌是常事，
只用时间戳会撞号，而撞号的表现是「删一条删掉了两条」。

### 接线

- 触发来源三种：`fav` / `playlist` / `page`（常量归 `pkg/online`，它们是记录表 schema 的一部分）；
- 写入方是**拦截层**（唯一的当事方），接口层只读与清 —— 所以是
  `intercept.Config.AutoDownloadLog`（往外推）+ `Server.SetAutoLog`（往里注），
  与 `SetMusicDL` / `SetRecommendLLM` 同一套做法；
- 接口：`GET /api/auto-download/records`（留给 AI 看「我收藏的歌怎么没下下来」）、
  `DELETE /api/auto-download/records`（`ids` 为空 = 全清；归 `internalEndpoints`，
  AI 不该自己去删用户的记录）；
- 响应带 `available` 字段：**「没有记录」与「功能没起来」必须分开说** ——
  界面上长得一样会让人以为功能坏了；
- 「音质下载」写 `auto_download_quality`（`highest` 默认 / `flac` / `320k` / `128k`）。
  固定档位是「正好那一档的候选排最前、没有就按原顺序兜底」，**不是**「拿不到就不下」——
  后者会让「收藏一首歌」变成「下载失败」。实际档位如实写进记录，用户看得见
  「要的是 128k、拿到的是 320k」；
- 界面：榜单管理里一个 `SelectField`（改完立刻生效，与勾选同一个口径），
  曲库管家新增「自动下载记录」页（多选 / 清除选中 / 一键清除），
  侧栏「任务状态」里一行「自动下载失败 N」**只报失败**（成功的那些是流水，
  当常态数字摆在侧栏只会让人习惯性忽略这一行）。

## 108 2026-10-07：⑤ 任务状态页的多选与一键清除

用户：「任务状态的几个页面中增加多选或者一键清除记录按钮。」

三处都改了：**下载队列**、**自动下载记录**、**推送同步历史**。

推送同步历史（曲库管家 → 推送 → 飞牛同步历史）：
后端 `push.Store` 新增 `ClearRuns(ids)` + `DELETE /api/push/runs`（`ids` 为空 = 全清），
前端表格加勾选框 + 「清除选中（N）」+「一键清除记录」。
⚠️ 它**只删历史、不动任务本身**的 `LastStatus` / `LastError` / `NextRunAt` ——
那些是「这个任务现在怎么样」，顺手清掉会让一个失败任务看起来像从没跑过，
而那正是用户最需要看见的信息（用例直接断言这几个字段不出现在 `ClearRuns` 里）。

下载队列页（`DownloadQueuePanel`）：

- 工具栏把原来的「清空完成」换成 **「清除选中（N）」+「一键清除记录」**；
- 勾选框**只出现在「已结束」的行上**（已完成/失败/已停止）—— 给正在下载的行也放一个，
  会让「清除选中」看起来像「取消下载」，而两个动作的后果差得远；
- `downloadManager` 新增两个方法：`removeTasks(ids)`（逐条走 `removeTask` = 真的取消，
  不是只从列表抹掉 —— 抹掉但后台还在写文件是更糟的结果）与 `clearRecords()`
  （只清已结束的，**不动**在跑/排队/暂停的；与 `clearAll` 的「停掉一切再清」分开）；
- 两个清除动作都问一句 `confirm`：清记录不可撤销，而两个按钮挨着放，误点一下就全没了。
  确认是**界面**的责任（service 只管做）。

### 过程里踩到并修正的两件事

1. **SSH 在 6828，不是 22**（用户告知）。HANDOVER §1.4 原先写着「飞牛没有 SSH（22 不通）」，
   把唯一的正路给否掉了 —— 于是前几轮只能绕 ego-browser 那条桥。已改。

2. **`appcenter-cli install-fpk` 对已安装的应用是空操作**。它打印
   `[Info]Application [yinshu-ai] is installed.` 然后什么都不做 —— 磁盘上二进制的时间戳与大小都不变；

   `uninstall_init` 会先把 `data/` 与 `.env` 打包到 `/vol1/yinshu-ai-backup-<ts>.tar.gz`，
   而 **`@appdata/yinshu-ai` 不会被卸载删掉** —— 卸载后 `data/config.json`、`data/online/downloaded.json`
   都还在。我另外还整份 `cp -a` 了一份到 `/vol1/yinshu-ai-appdata-backup-2.1.119`（642 MB，可随时删）。
