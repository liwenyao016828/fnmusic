## ① 换版本候选：提前检测能不能用

**问题**：搜索层只保证「搜得到」，解析层才知道「拿不拿得到直链」。中间没有闸门，列表里混着一堆点下去必然失败的版本——真机上就是那条 `这个版本取不到直链（kg/E8EE57D67169402710C4FF9259D841F）：该平台没有可用的直链解析器`。

**后端** `backend/pkg/intercept/repair.go`：

- 新增 `TrackProbeItem{Platform, PlatformID}` / `TrackProbeResult{Key, Platform, PlatformID, OK, Transient, Reason, Tier}`。
- `(i *Interceptor) ProbeCandidates(ctx, items)`：上限 `probeCandidateLimit = 40` 条、`probeConcurrency = 8` 并发、每条独立 `probeCandidateTimeout = 5s` 超时（一条慢不能拖死整批）。
- 判据：`pool.Supports` 不通过 → 「该平台没有可用的直链解析器」；`pool.ResolveLadder` 成功且 URL 非空 → `ok=true` + 档位；错误按哨兵分流 —— `ErrNoResolver` 判死、`ErrNotPlayable` 判死、`ErrTransient` 只标 `transient=true`（这次没拿到≠永远拿不到）、其他错误也归 transient 并把原文带上。
- **不下载、不写盘**；解析结果进 `online.Pool` 的 5 分钟正/负缓存，随后真点替换直接命中，不重复打上游。

**接口** `POST /api/library/repair/probe`（`backend/pkg/api/repair.go` 的 `handleRepairProbe` + `SetRepairProbe` 注入点，`backend/main.go` 在 `ic != nil` 块内注入）：body `{"items":[{platform, platform_id}]}` → `{items, checked, ok_count}`。

**前端** `frontend/src/components/RepairCandidateSheet.vue` + `frontend/src/services/repairList.js`：

- 搜完立刻 `probeRows(gen)` 预检前 40 条；`probeGen` 代际号保证重搜时上一轮的迟到结果被丢弃。
- 稳定判死的行置灰（`opacity-50` + `disabled`），歌名下用红字写原因，`title` 补全；**故意不重排**——几秒后行在光标下位移会导致误点覆盖（宁可位置稳定，需要「只看可用」再另做筛选）。
- 底部一行汇总：「已检测前 N 个版本：X 个可用，Y 个用不了（已置灰），Z 个暂时取不到」。

## ② 排序、标签与搜索词

**搜索框只填歌名**（`candidateKeyword` 重写）：真机上「你瞒我瞒 - ls 某某」搜出 107 个版本，纯歌名更准。现在去曲序前缀 → 按 ` - ` / `–` / `—` / `_` / `|` 切首段 → 去掉括号补充 → 折空格；`artist` 形参保留但不参与（调用方签名不变）。placeholder 改成「歌名（只填歌名，搜索更准）」。

**排序**（`candidateRows(list, wantSec, {keyword, artist})`）：匹配度降序 → 原唱优先（`versionRank`：原唱 2 > 翻唱 1 > 未知 0）→ 音质档位降序 → 时长接近 → 名称。

**原唱 / 翻唱标签**（`versionLabel(name, singer, keyword, wantArtist)`）：

- 歌名跟搜索词不沾边 → 不标（避免给一堆无关版本乱贴标签）。
- 歌名里含「翻唱 / cover / 翻自」→ 翻唱。
- 拿不到原歌手信息（本地文件没 artist）→ 不标，不猜。
- 歌手归一化后相同或互相包含 → 原唱，否则翻唱。

**标签跟随主题色**：原唱 chip 用 `bg-[var(--ys-accent-soft)] text-[var(--ys-accent)]`，翻唱用 `bg-[var(--ys-surface-sunken)] text-[var(--ys-text-muted)]`，圆角胶囊 + 10px。主题切换只改 `--ys-accent-*` 一族变量，chip 自动跟着变，没有写死颜色。

## ③ 失败原因不再被吞成「参数不对」

**根因** `frontend/src/services/userMsg.js`：`usableMessage()` 见长度 > 40 或含 `/api/`、堆栈、英文 Error 就判不可用，随后 `shortReason()` 按状态码回退到 400/422 → 「参数不对，请检查填写内容」。后端那条中文原因（带 `kg/E8EE…` 的 ID）刚好两条都踩，于是被换掉。

- 抽出 `hasTechTrace(s)`；新增 `trimForUI(msg)`：剥掉括号内含 `/` 或 8 位以上十六进制/数字的技术片段，折空格、修首尾标点，再截到 40 字。
- 新增导出 `reasonFromServer(body)`：能直接用就用，否则先修剪再说；`shortReason` 的 response 分支改用它。

效果：同一条 400 现在显示含「直链解析器」的短句，用户看得懂该换一个版本。

## ④ 修复进度卡片（已修复 / 总数）

**口径**（用户确认）：已修复 = 总歌曲数 − 当前仍待修的条数，本来正常的歌也算完成。

**后端**：

- `backend/pkg/intercept/repair_store.go`（新）：把修复清单扫描结果落盘成 `repair_scan.json`（`tmp` + `rename`，失败只记日志不影响返回）——进度条不能每次刷新都触发全库重扫。`AudioRepairFacts(dir)` / `AudioRepairBreakdown(dir)` / `QualityFacts(dir)` 都按目录校验：快照目录跟当前不一致就回 `known=false`，换过目录绝不给旧数字；`underDir()` 前缀必须带 `/`，`/vol1/Music2` 不算在 `/vol1/Music` 下。
- `updateRepairScanAfterReplace(oldPath, newPath)`：换版本成功后从快照里剔掉旧路径，再按新文件重判，仍不合格就留一条 —— 否则「已修复」数字要等下次全扫才动。
- `backend/pkg/api/tidy_progress.go`（新）：`GET /api/library/repair/progress?dir=` → `{dir, total, items:[meta, audio, quality]}`。meta 直接读索引的 `FieldGaps`（分母 = 能写标签的文件数，写不进标签的另计并写进 note），audio/quality 读上面的快照。

**前端** `frontend/src/components/TidyProgress.vue`：按页面拆开的卡片组（`group` = `meta` / `audio` / `quality`），每组一横排小卡（总数 + 各细项，数字带「首」）；没扫过时显示虚线卡「这一类还没有扫描结论 · 先点上面的『扫描』」。挂载位置：补全段（替换掉原 StatLine）、修复段、音质段各自页内，不再在页头挂一条全局总数。补全页按用户要求去掉了「还缺」卡，修复页保留（那页「还缺」是修复任务的核心信息）。

## ⑤ 整理页：音质检测（格式 / 体积 / 码率对不对得上）

**后端** `backend/pkg/api/audio_audit.go`（新）三个接口：

- `POST /api/organize/audio-audit` `{dir}` → 逐条 `audioprobe.Probe` 比对「声称 vs 实际」：文件过小（< 12 B）无法识别；扩展名声明的容器与实际魔数容器不符；无损文件等效码率 < 200 kbps（疑似假无损或截断）；有损文件等效码率 < 48 kbps 且时长 > 30s（疑似低码率或截断）。
- `POST /api/library/repair/duration` —— 单文件实测时长。
- `POST /api/library/repair/version-audit` —— 见下节。

**前端** `frontend/src/components/OrganizeView.vue`：新增「音质检测」卡，列出异常行（标题 / 歌手 · `flac → 未知容器` · 体积 · 时长 · 标称 x / 等效 y kbps + 红字问题），每行「替换」（复用换版本抽屉）「删除」（走回收站），标题可点播放（`emit('play', {song, playlist, index})`，`App.vue` 给 `OrganizeView` 补了 `@play="playSong"`）。

**注意口径**：码率和容器只能提示异常，不等于听感结论；MP3 头里的码率只是首帧标称，没有 Xing 头时时长靠体积推算，所以「标称 vs 等效」不一致不当成假码率的证据。

## ⑥ 修复页：版本时长核对

`POST /api/library/repair/version-audit`：最多 20 条，每条取本地实测时长，再去原生四平台（wy/tx/kg/kw）搜同名候选（每首总预算 8s），取时长差最小的比对：

- 差 > 5s → 「与同名平台候选时长相差较大，可能是不同版本」
- 否则 → 「时长接近；仅供核对，不代表已确认同一版本」
- 没有候选或本地时长测不出 → 「没有足够的同版本证据」

前端在修复清单表格后加了「版本时长核对」块：点「开始核对」跑当前可见行（最多 20 条），结果行写「本地 mm:ss / 平台 mm:ss / 状态 chip / 原因」。**时长接近不是内容证明**——现场版、翻唱、剪辑版都可能撞时长，所以文案始终是「可能」而不是「已确认」。
