## v2.18.1 白屏热修 + 历史保留上限

### 1. 白屏根因：模块求值期的 TDZ

`frontend/src/services/downloadManager.js` 里有一句模块级监听：

```js
watch(backendDownload.items, syncTasks, { immediate: true })
```

`immediate: true` 让它在**模块求值阶段**就同步跑一次 `syncTasks()`，而 `syncTasks` 末尾会调
`persistUnsent()`；`persistUnsent` 的第一行是

```js
if (!unsentReady) return
```

`unsentReady` 原本声明在文件后半段（`let unsentReady = false`），于是这次调用撞进 TDZ，抛：

```
ReferenceError: Cannot access 'unsentReady' before initialization
```

模块初始化失败 → `main.js` 整条 import 链断掉 → `#app` 一个子节点都没有，页面白屏。

为什么之前没发现：改完是走 HMR 热更的，模块图没重建，一切正常；**只有全新加载（刷新/首次打开）才复现**。`npm test` 与 `vite build` 都不执行模块求值顺序，天然拦不住。

### 2. 修法

把 `let unsentReady = false` 挪到那句 `watch(...)` **之前**，并在注释里写清楚「必须早于 immediate watcher，否则白屏」，避免以后有人整理变量声明顺序时又挪回去。`persistUnsent` 里原有的「模块加载时别把磁盘上的未确认提交擦掉」判断保持不动。

### 3. 回归测试

`frontend/src/services/downloadManager.init.test.mjs`（新增 2 个用例）：

- `let unsentReady` 的声明位置必须**早于** immediate watcher（按源码字符位置比较）；
- 文件里只允许出现一处 `let unsentReady`。

自检：把声明挪回 watcher 之后，该测试立刻红（实测 `# pass 1 / # fail 1`）；改回来 2/2 绿。

### 4. 历史保留上限 200 → 500

`backend/pkg/backenddl/queue.go` 的 `limitTerminal` 是「已结束记录」上限，每次状态变化按 `UpdatedAt` 从旧到新裁。

实测问题：老版本把队列记在浏览器里，这台机器上的旧队列有 266 条；迁移进后台队列时按 200 裁，**58 条成功历史 + 8 条失败里的最旧部分被静默丢掉**，用户点了「一键清除」之类的入口都看不到它们了。

- 上限改 500（500 条 JSON 也就几百 KB，不值得为体积丢用户记录），注释里写明这个数字的来历；
- 新增 `TestTrimKeepsNewestHistory`：迁移 `limitTerminal + 12` 条历史，断言「条数裁到上限」「最旧那条没了」「最新那条还在」。

已丢掉的 66 条记录无法恢复（浏览器那份已按迁移协议删除、后端 JSON 也已裁过），只能在以后避免。

### 5. 验证

- 前端：`npm test` **397/397**；`npx vite build` 6.80s 通过；
- 后端：`gofmt -l` 空、`go test ./pkg/backenddl/` ok；
- 真机（dev 后端 8900 + 内嵌 dist，相当于安装包形态）：全新打开 `#app` 子节点 1、页面正常渲染；下载页显示「后台下载 就绪 / 8 失败 / 192 已完成」「按序号选（共 200 行可勾）」，200 行列表正常；
- 迁移实测：刷新后 `fn_download_tasks_v1` 从 217245 字节清零、`fn_backend_queue_migrated_v1=1`、`POST /api/download/backend/submit` 200、后台队列 `success 192 / failed 8`。

### 6. 教训

模块级 `watch(..., { immediate: true })`、`computed` 之外的立即执行代码，都可能在**某个 `let`/`const` 还没初始化**时被调用。凡是「模块求值阶段会跑」的函数，它触碰的模块级状态必须声明在调用点之前——这类顺序依赖应该用源码顺序测试钉住，别指望 HMR 期间能发现。

### 1. 文件名体检：修「文件夹显示未知错误」

**根因**：下载落盘时若歌曲标签里带 GBK 脏字节，Go 会把非法 UTF-8 原样写进文件名；fnOS 的文件/媒体接口按
UTF-8 处理名字，遇到非法字节**整层目录**直接报错 —— 所以表现是「文件夹未知错误」而不是「某首歌显示不出来」。
下载侧早已在 `pkg/filename` 里堵住新数据，但盘上已有的坏名字得能查能修。

- 后端 `backend/pkg/nas/health.go`：`ScanHealth` 分类 `bad_utf8` / `control_char` / `illegal_char` /
  `trailing_dot` / `too_long` / `zero_byte` / `leftover_part` / `no_permission` / `not_regular` /
  `broken_symlink` / `unreadable_dir`；上限 20 万条目、500 条问题；按「名字类更严重」排序。
- 路由 `/api/nas/health/scan`（只读）与 `/api/nas/health/fix`（改名 / 删除 / chmod），已登记 catalog。

### 2. 修复接口为何收 `id` 而不是 `path`（这轮最关键的坑）

第一版按 `path` 回传，真机一测就露馅：**非法 UTF-8 的文件名过一次 JSON 就变成 U+FFFD**
（`encoding/json` 对无效字节是替换而不是报错，`��` 已经回不到原字节），后端拿去 `os.Stat` 必然
失败 —— 恰好是最需要修的那一类修不了。实测报错：`拒绝处理：路径不存在或不可访问: .../bad<?>song.mp3`。

改法：scan 给每条 issue 一个 `id`（路径原始字节的 `base64url`），fix 只收 `ids`，服务端在**最近 8 次扫描的
内存缓存**里回查真实字节路径；查不到就返回 409 让前端提示「重新扫描」（进程重启后缓存失效）。
副产品是安全性变好了：客户端再也不能靠伪造路径让服务端删文件。

同时发现 `pathguard.ResolveSafePath`（走 `EvalSymlinks`）会判「首尾空格」这类名字不可访问，而那也是要修的，
所以缓存来源的路径改走 `trustedIssuePath`：词法包含 + **父目录** `EvalSymlinks` + `Lstat`
（父目录才是可能被换成软链接逃逸的那一层，文件名保持原样）。老客户端不带 id 时仍走通用校验。

另外两处顺手修：
- **dry-run 不再谎报**：以前 `dry_run` 把 `OK` 置 true，调用方按 OK 数报「已修好 N 条」，用户以为改完了。
  现在回报 `would_fix`，并且不改动任何文件。
- **目录权限修复用 0755**：以前一律 0644，修完权限 000 的目录依然进不去；`unreadable_dir` 也从
  「需人工」改成可修（属主不对时会如实失败）。

- 前端 `frontend/src/components/LibraryHealthCard.vue` 挂在「补全整理 → 体检」；
  「本地曲库」工具栏加「体检文件名」入口（`NasExplorer.vue` 的 `openHealthCheck`，写 `nas_health_dir`
  偏好后 `navigateTo('tidy','audit')`）—— 用户看到报错的地方就在那儿，功能藏别的页面等于没修。
- 测试 `frontend/src/services/libraryHealth.test.mjs` 6 例，其中一条专门钉「payload 只送 id，不送 path/issues」。

**浏览器复验时又抓到一个 bug（2.19.1 修）**：在「本地曲库」点「体检文件名」时，卡片扫的却是"补全整理"
自己那份曲库目录 —— 入口只把目录写进 localStorage 偏好 `nas_health_dir`，而卡片优先用 `props.dir`
（= `tidyDir || nasDir`），偏好永远轮不上；即使轮上，用户之后在别处改了曲库目录，体检还会翻旧路径。
改成一次性传递：`navigateTo('tidy', { segment: 'audit', healthDir: 当前目录 })`，`TidyView` 用
`onNavigate` 接住并只在本页停留期间保留（`watch(currentView)` 离开即清），卡片不再读偏好。
为此给 `navBus.navigateTo` 补了「对象 payload 里的 `segment` 也切分段」这条路径（以前只有字符串形态能切，
这正是当初被迫塞 localStorage 的原因），并新增 `frontend/src/services/navBus.test.mjs` 6 例钉住两种形态 +
payload 透传 + 分段不认识时不切。顺带把 `autoDownload.test.mjs` 里那条「TidyView 从 navBus 导入」的
字符串断言改成正则 —— 它原本硬编码整行 import，加一个符号就红，属于测试写得太死。

**真机 e2e（dev 后端 8900）**：造 `bad\xff\xfesong.mp3` / `ctrl\x01name.mp3` / `trail.mp3 `（尾空格）/
`zero.mp3`（0 字节）/ `song.part` / 权限 000 的 `locked/` 六个案例 →
scan 全数识别（6 条）；`dry_run` 得 `fixed=0 would_fix=6` 且目录内容未变；
真修 `fixed=5`（locked 属主受限需人工），目录变成 `bad_song.mp3` / `ctrlname.mp3` / `trail.mp3`，
`zero.mp3` 与 `song.part` 已清；重扫 0 条。
