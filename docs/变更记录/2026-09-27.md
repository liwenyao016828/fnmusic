**一、502 的三层根因（都在后端出站链路上，逐层剥）**

第一层 —— **我们自己的 SSRF 守卫拦下了用户自己配置的代理出口**。
浏览器取链打的是 `POST /api/proxy/http`（`backend/pkg/api/routes.go:62` → `backend/pkg/proxy/http.go`），
直接 curl 该端点拿到原文：

```
Post "https://c.wwwweb.top/music/url": proxyconnect tcp: dial tcp 192.168.1.3:7890: 禁止访问内网/元数据地址 192.168.1.3
```

`pkg/security` 的 `Dialer.Control` 只判「目标是不是私网」，可当请求经代理发出时，
Control 看到的是**代理自己**的地址（`192.168.1.3:7890` 正是内网）—— 于是公网出站全死。
`proxyFunc` 早就按目标分流（内网直连、公网走代理），缺的只是「代理本身不是 SSRF 目标」这一步。

- 新增 `proxyExemptAddrs()`：读 `HTTP_PROXY/http_proxy/HTTPS_PROXY/https_proxy/ALL_PROXY/all_proxy`，
  归一化成 `host:port`（无端口时 https→443、其它→80）；
- `dialControl(opts, exempt)` 在原有判断前加一句 `if exempt[normalizeAddr(address)] { return nil }`；
- `NewSafeTransport(opts)` 变成 `newSafeTransport(opts, proxyExemptAddrs(), proxyFunc(opts))` ——
  **豁免表与 proxy 函数都可注入**，因为 `http.ProxyFromEnvironment` 在进程内只读一次环境变量、测试里改 env 无效
  （第一版测试就是这么 FAIL 的，报的还是上一次锁定的代理地址）。
- 豁免是**固定白名单**：没配在环境里的私网地址（`10.x` / `169.254.169.254` / 别的内网端口）照旧拦。

第二层 —— **代理的 HTTPS / CONNECT 通道坏了**：
实测 `curl -x http://192.168.1.3:7890 http://1.1.1.1/` → 301（明文通），
`curl -x … https://example.com/` → `SSL_ERROR_SYSCALL`（隧道不通），Go 侧表现为 `EOF`。
而后端对公网**无条件走代理**，所以取链全挂在代理上。

- 新增 `proxyFallbackTransport{proxied, direct http.RoundTripper; proxyFor func(*http.Request) (*url.URL, error); attemptTimeout time.Duration}`：
  先经代理试；只在「**没拿到响应** + 是连接层错误 + 请求体可重放」时用 `req.GetBody()` 克隆请求**直连重试一次**；
  拿到任何响应（哪怕 502）都**不重试** —— 避免重复投递；直连也失败则返回**代理那条**原始错误。
- `isProxyConnError(err)`：`io.EOF` / `syscall.ECONNREFUSED|ECONNRESET|EHOSTUNREACH|ENETUNREACH|ETIMEDOUT|EPIPE` /
  `net.Error`（超时、临时） / 文案含 `proxyconnect`、`connection refused`、`no route to host`、`i/o timeout` 等。
- 单次「经代理」上限 `proxyAttemptTimeout = 5s`，失败后进 **60s 冷却**（`proxyFailUntil atomic.Int64`）：
  冷却期内 `proxyFunc` 直接返回 nil，所有请求走直连，不再让每个请求都先卡一下。
- 两个导出构造：`NewSafeRoundTripper(opts)`（普通调用，有 5s 上限）与
  **`NewSafeStreamRoundTripper(opts)`（流式中继专用，无上限）** —— 否则 `context.WithTimeout` 会在 5s 后掐断长音频响应体。
  `pkg/api/server.go` 的 `streamClient` 改用后者；`NewSafeClient` 改用前者。

第三层 —— **出站 HTTP/2 被 CDN 边缘挂住**（这层最隐蔽，靠探针程序测出来）：
拿 `.dev/probe` 里一个直接调 `security.NewSafeClient` 的小程序连打同一 POST：

```
[0] status=200 elapsed=2.806s
[1] status=200 elapsed=5.370s
[2] err=... http2: timeout awaiting response headers elapsed=20.002s
[3] err=... 同样 20.001s
```

`newSafeTransport` 里写着 `ForceAttemptHTTP2: true`，而该站挂在 openresty / EdgeOne 边缘上：
宣告支持 h2，却把 Go 的 h2 客户端挂到 `ResponseHeaderTimeout`（20s）才失败；
同一地址用 `curl -4`（HTTP/1.1）只要 **0.23s**。改为 `ForceAttemptHTTP2: false` 后：

```
[0] status=200 elapsed=5.327s   ← 第一发仍付一次 5s 代理上限
[SECURITY] 代理 192.168.1.3:7890 不通（EOF），已改用直连：c.wwwweb.top（1m0s 内不再尝试代理）
[1] 226ms   [2] 101ms   [3] 191ms
```

后端侧复测：`POST /api/proxy/http` 取链 → `http=200 total=2.39s`，body 是真实直链。

**三、真机验证（浏览器在 NAS → 开发机 vite，逐条对着交付项）**

- ②「下一首」：点播放条 `button[title="下一首"]` 后抓 XHR —— 解析请求是
  `source=tx, musicId=001zMQr71F1Qo8`（第 1 行）**接着** `source=kg, musicId=16C8AB298231370293D16BCF9E5FF9B6`（**列表第 2 行**），
  不是随机另一首 ⇒ 语义已回到「当前页面歌单的下一首」。
- ③不弹大屏：整轮采样 `div.fixed.inset-0.z-50` 计数恒为 0；再手动点顶栏「打开播放器」→ 立即出现（计 1，收起按钮「收起」在位）⇒ 该开的时候还能开。
- **遗留（未改，属上游数据质量）**：现用音源脚本（`custom_1789639383`「聚合API接口 v3」）对 `kg` / `tx` 源解析出来的直链，
  都落在 `cdn-img.gitcode.com` 上、**固定 171,072 B ≈ 7.1 秒**的占位片段（三个不同 songmid 字节数完全相同）；
  同一接口的 `kw` 源正常（`car-bj.kuwo.cn`，3.4 MB 完整曲）。**我们的中继没有截断**：
  `GET /api/player/stream?url=…` 与源站字节数一致（171,072 / `Content-Length: 171072`）。
  所以「点 tx/kg 行的歌听 7 秒就跳」目前是上游给的片段，不是链路 bug；要不要在播放侧做「疑似试听片段就换源」由用户定。

**五、可复用手法**

- 出站链路「到底是哪一层慢/挂」别在 HTTP 层猜：写个 `main.go` 直接调 `security.NewSafeClient` 计时，
  再对比 `env -u HTTP_PROXY -u http_proxy -u HTTPS_PROXY -u https_proxy -u ALL_PROXY -u all_proxy curl -4 …`（清代理直连），一次就能定位。
- 浏览器侧 LX 运行时的请求走 **axios(XHR)**，`window.fetch` 埋点抓不到；要抓就得 hook `XMLHttpRequest.prototype.open/send`。
- **别在同一条命令里既 `pkill -f 'fn-dev-backend …'` 又 `go build -o ../.dev/fn-dev-backend`**：
  包装 shell 的命令行含同样字符串，会把自己也杀掉（本轮复现过一次）。停 dev 后端用 `job_kill`。
