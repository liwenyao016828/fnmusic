## 69 2026-10-05：虚拟歌单上线（每日推荐 / 热门推荐）→ **v2.1.73**

飞牛音乐的歌单区顶部出现**每日推荐**与**热门推荐**。两个歌单由拦截层**实时造**，官方库一行不写；
对外**只读**（改名/删除/加歌一律透传，官方按「歌单不存在」拒绝）。

- 新建 `backend/pkg/intercept/vplaylist.go`：`online:playlist:daily:<YYYYMMDD>:<用户前缀>`（种子 =
  播放历史里听得最多的歌手，没有历史时退回收藏，再用按日期轮换的关键词补足）、
  `online:playlist:hot:<YYYYMMDD>:<用户前缀>`（网易公开榜单**热歌榜** `3778678`，免登录）、
  `online:playlist:nm:<id>`（任意网易公开歌单）。
- 硬约束：曲目必须能播才进列表；已收藏的排除；**空歌单不注入**；曲目 id 仍是 32 位纯 hex；
  官方 `playlist/detail` 与 `track/playlist-detail/list` 对虚拟歌单**一次都不打**；
  写端点一律透传、**绝不写本地桶**。
- `Config` 新增 `NeteasePlaylist` 注入口 —— 推荐歌单会在**每次列歌单时**被算一次，不注入会让整个
  测试套件依赖外网。
- 新增 `pkg/intercept/vplaylist_test.go` 六条；**证明有效**：去掉 detail 端短路后
  `TestVirtualPlaylistDetailServedLocally` 立刻报 `name 不对：""` 与「不该打上游，却打了」。
- 真机（NAS，`2.1.73` 已安装并接管）：`playlist/list` → **「每日推荐 10-06」20 首 + 「热门推荐」23 首**，
  `total 2`；每日推荐 `size=3` 分页正确、`size=-1` 全量 20；两条歌单的曲目 guid **全部 32 位 hex**；
  对虚拟 guid 的 `playlist/delete` 被官方拒绝（`code:100002`）。
- 顺带查清：之前歌单区那条「每日推荐」是 `fnmusic-ext` 现造的（它的 `recommend.py` 全是 `mode=ro`），
  我们仓库里 `online:playlist` 出现 0 次，官方 `playlist` 表 0 行 —— 所以不会和官方库打架。

### ⚠️ 同轮发现但**故意没修**的潜伏 bug：`userKey` 一直退回 `fp-` 前缀

`pkg/intercept/intercept.go` 的 `probeUserGUID()` 用
`http.NewRequestWithContext(ctx, GET, apiPrefix+"/user/me", nil)` 构造请求 —— 那是**相对 URL**。
真机上的 `Upstream` 是 `takeover.UnixClient()` 返回的 `*http.Client`，而 `http.Client.Do`
**不接受相对 URL**（当初 `forward` 就是这么变成「空 body 502」的，已修为绝对 URL）。
后果：探测永远失败 → `userKey()` 一直落到 `fp-<凭据指纹前16位>` 兜底。

真机证据：`playlist/list` 里的虚拟歌单 guid 是
`online:playlist:daily:20261006:fp2a7fef803c`（应是官方 user guid 的 `9db86e47dc0d`），
而同一时刻直接 `curl --unix-socket … /music/api/v1/user/me` 能正常拿到
`{"code":0,…,"guid":"9db86e47dc0d4fa8a1bfaac1dabac9f5"}`。

**为什么不在这版修**：`userKey` 是在线存储（收藏 / 歌单附加 / 播放历史）的分片键。
现在磁盘上的数据全部按 `fp-…` 存着，一旦改成真实 guid，**用户已有的在线收藏与歌单附加会看起来全部消失**。
所以必须先定迁移方案（或明确接受重置），再动这一行 —— 不能当作普通 bug 顺手改。

同轮还修了：`server.go` 的 `CurrentVersion` 与 `fpk-package/manifest` 的 `version` —— 第一次编辑静默失败
（`Error: cannot edit … file changed since it was read`），结果打出来的包二进制报 `2.1.72` 而 manifest 是
`2.1.73`。**教训：四处同步必须逐个回读确认，不能假设编辑成功。**

## 67 2026-10-05：修 `isFavorite` 写死 → **v2.1.72**

**根因**：官方前端**不查收藏接口**，而是从列表反推收藏集合 ——
`favoriteIds = list.filter(x => x.isFavorite).map(x => x.guid)`（官方 bundle 里 82 处 `isFavorite`）。
我们的 `pkg/online/vo.go` 的 `FavoriteVO` **硬编码 `"isFavorite": true`**，而**收藏列表 / 歌单附加曲目 /
播放历史共用同一个构造器**（`favorite.go:86`、`playlist.go:184`、`history.go:45`）
→ 歌单和历史里**每一首**在线曲目红心全亮，哪怕从没收藏过。

**修法**：状态由调用方传 —— `FavoriteVO(t, pb, createdAt, isFavorite, template)`；
收藏列表传 `true`（按定义都在里面），歌单/历史传 `favorites[it.Track.FakeID()]`，
`favorites := i.store.FavoriteGUIDs(i.userKey(r))`（`search.go:117` / `metadata.go:42` 早就在用这个模式）。
顺带补上 `source` 与 `is_online: true`。

**证明测试有效**：把两处改回硬编码 `true` →
```
--- FAIL: TestOnlineIsFavoriteReflectsStore
    intercept_test.go:1118: 歌单：243e178fa7583b4b1e0128c11d0dd772 的 isFavorite 应为 false，得到 true
```

**顺带确认**：`is_online` 在官方前端出现 **0 次** —— 官方 UI 根本不读，属契约一致性问题，不是功能 bug。

**真机复验**（NAS，2.1.72）：歌单里未收藏 → `false`、收藏过的 → `true`、两者 `is_online: true`；
历史同样；收藏列表按定义 `true`。交付 `yinshu-ai-2.1.72.fpk`，6,594,831 字节，
sha256 `88bb30960aebbd890c6de3b0b195ccf5ededa87e051817f5a65eb23af1043783`。

## 66 2026-10-05：接管层两个只有真机能暴露的 bug → **v2.1.71**

2.1.70 在开发机全绿，装到飞牛上却接不了管。上真机挖出两个都跟「开发机 / NAS 环境差异」有关的 bug。

### bug 一：`invalid cross-device link`（EXDEV）

```
[TAKEOVER] 未接管音乐入口：takeover: 发布失败，已回滚: invalid cross-device link
```

staging socket 建在了 `--data` 目录（真机 `/vol1`），而发布那步 `rename(staging, target)`
的 target 在 `/var/run` —— **`rename(2)` 不允许跨文件系统**。

**修**：`stageListener()` 改为在 `filepath.Dir(m.opts.Target)` 下建 `.qulv-stage-<pid>.sock`；
新增 `sweepStaleStaging(dir)`（清 `kill -9` 残留）与 `dropStaging(ln)`（失败路径真删文件，
因为 `listenUnixNoUnlink` 故意不删）；`publish` 里 6 处 `_ = staging.Close()` 全换成 `dropStaging`。

> **验证手段本身的坑**：GNU `mv` 跨文件系统会退化成「复制 + 删除」，看起来成功；
> 必须用 `python3 os.rename` 才能看到 `errno 18`。开发机一直是绿的，是因为 `--data /tmp` 和 socket 同挂载点。

### bug 二：接管之后入口 socket 权限变窄，非 root 客户端全被挡住

入口从官方的 `srw-rw-rw-`（0666）变成 `srwxr-xr-x`（0755，继承 umask 022）。
**root 连得上、日志干净**，但 uid 895 直接 `Failed to connect` ——
即「接管看起来成功，实际只有 root 能打开音乐」。

**修**：`publish()` 在动 socket 前 `os.Chmod(stagingPath(staging), socketMode(m.opts.Target))`；
`socketMode(path)` 读官方当前权限位，官方不在才退回 `0666`（官方收紧就跟着收紧，不写死）。

### 顺带修的诊断问题

「接管失败」和「没开启」在 `/api/takeover/status` 上长得一模一样（都 `enabled:false` +「设 `QULV_TAKEOVER=1`」），
真机上照着这条去查环境变量白跑一趟。新增 `Server.takeoverErr` + `SetTakeoverError(err)`，
失败时回 `enabled:true` + `error` + 原因。

**真机验证**：独立跑 2.1.71 → 接管成功、入口 socket `666`、非 root `uid 895` 打
`/_qulv/livez` → `{"service":"qulv-takeover","pid":564165}`；`kill -TERM` 优雅交还官方入口、`/var/run` 无残留。

## 64 2026-10-05：接管层阶段 ① —— socket 接管 + 全透传 + 回滚 → **v2.1.67**

`pkg/takeover`：官方音乐应用被 nginx 通过 `proxy_pass http://unix:/var/run/trim_music.socket:` 访问。
本应用把官方入口 rename 成 `/var/run/trim_music_upstream.socket`，自己绑原路径 ——
于是官方音乐的所有请求都先经过我们，认得就处理、认不得就原样透传。

- **崩溃安全**：先写 journal（`<data>/takeover.lock`）再动 socket；`kill -9` 后重启能接回。
- **优雅还原**：`SIGTERM` 时把官方 socket 换回原路径并退出。
- **让路约定**：若入口已被别的扩展代理，本应用**拒绝接管**并透传（`yielded`）——
  两个扩展在 socket 层互斥，用户「二选一，谁用谁开」。
- 提供状态 / 还原接口。

**阶段边界是刻意的**：接管层是唯一能让官方音乐打不开的组件，所以单独一个版本上线、单独被验证。
