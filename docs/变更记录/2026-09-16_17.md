#### ① **导入校验误杀混淆脚本**（用户报的直接原因）

报错原文：「导入完成: 成功 0 个 · 失败 1 个 —— 没有找到音源脚本的注册标识」。

根因：`pkg/sources/validate.go` 扫源码文本，要求出现 `lx.on(` / `lx.request` /
`globalThis.lx` 等**明文标记**。而真实音源大量经过 VM 混淆，标识符是用
`\u006c\u0078`（"lx"）这类转义拼出来的 —— 实测 `lx-music-source-v6 (修复).js`
**七个标记全部不命中**，被拒在导入之外，而它在别的播放器完全能用。

**觅音怎么做的**：`loadLxSource()` 里**完全没有**基于源码文本的音源识别。
它把脚本丢进 `node:vm` 执行，然后：
1. 等 `lx.send('inited')`（`initPromise` vs `INIT_WAIT_MS`），超时报
   「音源初始化超时（Nms 内未发送 inited）」
2. 查 `handlers.length`，为空报「**音源未注册 musicUrl 处理函数**」
3. `platforms` 为空时**兜底成** `["wy","kw","kg","tx","mg"]` 而不是报错

**改法**：`ValidateScriptContent` 只做粗筛（空 / HTML / 过短 / 超 2MB / 整段是网址 /
完全没有 JS 语法特征），「是不是合格音源」交给运行时判定。
回归测试 `TestValidateScriptAcceptsObfuscatedScript` 用一份**不含任何明文标记**的
最小混淆脚本钉住这条 —— 并且测试里先断言样本确实不含明文标记，否则测试就没意义了。

> ⚠️ 这条是「**判据写错方向**」的典型：我们想拦的是「根本不是脚本的东西」，
> 却用「必须含有某些字符串」来表达 —— 而混淆正是为了不出现这些字符串。

### 上一轮（2026-09-17 深夜 ⑤）：查清「音源还是跑不了」的真实归属 + 修两处会误导排查的地方

用户反馈两条：「飞牛音乐连接不上」与「同一个音源 js 文件还是无法在这个项目上运行」。
**结论是这两条都不是运行时兼容性问题**，但排查过程中确实揪出两个我们自己的 bug。

#### ① 「音源跑不了」的归属：**用参考实现做了逐平台对照，结论是上游的锅**

用户给了脚本原件 `lx-music-source-v6 (修复).js`（洛雪格式、VM 混淆，md5 `bad0bcf…`）。
同一份脚本，两边跑，逐平台比对：

| 平台 | **本项目（浏览器沙箱）** | **忠实复刻的觅音沙箱**（`/tmp/lxtest/miyin-sim2.mjs`） |
|---|---|---|
| wy | ❌ `unknow error` ← 上游 nginx **502 Bad Gateway** | ❌ 同左，**502 Bad Gateway** |
| tx | ❌ `get music url failed` ← 上游 `{"code":2,"msg":"Object trans failure: 140017."}` | ❌ 同左，**同样的 code 2 原文** |
| kg | ✅ 拿到真实直链（`fsdg360.hw.kugou.com/...`） | ✅ 同左 |
| kw | ❌ `unknow error` ← 上游 nginx **502 Bad Gateway** | ❌ 同左，**502 Bad Gateway** |

**三次重复，两边结果稳定一致。** 请求 URL 的结构也完全一致
（`https://88.lxmusic.xn--fiqs8s/v4s/url/{平台}/{id}/{音质}?e=…&to=…&fp=…&s2=…`，
签名正常算出来了，没有 `sign=fail`）。

→ **不是运行时兼容性问题**：脚本能加载、能注册、能签名、能发请求、能收响应，
失败信息来自**音源自己的服务端**（wy/kw 上游 502、tx 上游业务错误码）。
用觅音 / 洛雪桌面端跑同一个脚本，结果一样。

> ⚠️ **一个差点把人带偏的坑**：本项目默认导入了 8 个音源，`getMusicUrl()` 会**轮询**。
> 单独看日志时会看到「wy/tx/kw 都成功」—— 那其实是**别的音源（ikun）抢答了**，
> 不是被测脚本。**必须用 `probeSource()` 直接调它自己的 handler**（绕开轮询），
> 结论才可信。判断依据：日志里的接口域名（ikun 用 `c.wwwweb.top`，本脚本用 `88.lxmusic.xn--fiqs8s`）。

> **判据**：脚本能加载、能注册 handler、能发出请求、能收到响应 →
> **不是沙箱兼容性问题**，剩下的差异只可能在上游。
> 要更强的话，就把它丢进参考实现的沙箱跑一遍做对照 —— 逐平台一致即可定论。

**顺带发现**：用户此前导入的 `[独家音源] v4` 已被作者废弃 ——
服务端更新检查原话「当前源脚本版本过低(v4)，请下载最新版本(v6)」，
取链请求带 `sign=fail` 且 `/lxmusicv4/...` 返回 404。换 v6 是对的，但 v6 的 wy/tx/kw 依然受上游所限。

#### ② 真 bug：`loadScript()` 不等异步注册，会把好音源判成坏的

**相当一部分音源是「两段式」的**：脚本先异步拉远程配置 / 校验版本，
拿到结果后才 `lx.on('request', ...)`。实测那个 v6 脚本在 `loadScript()` 返回后
**约 250ms** 才注册（实测 `hasHandler` 立刻查是 `false`，259ms 后才是 `true`）。

后果很具体：`_callHandler()` 在 handler 缺失时直接抛「音源尚未就绪」，
而 `SourceManager.probeOne()` / `probeSource()` 会把这次**误报记成一次失败并计入熔断** ——
于是「一键清理失效音源」会把完全正常的音源杀掉。这是**静默的竞态 bug**，只在窗口期内出现。

修复：`lx-runtime.js` 新增 `waitHandler(sourceId, timeoutMs)`（默认 2s），
`_callHandler()` 在 handler 缺失时先等再判定。
**回归测试**：`frontend/src/engine/lx-runtime.test.mjs`（4 例，`node --test` 跑）。

> 顺手把 `lx-runtime.js` 里的本地 import 都补上了 `.js` 后缀 ——
> Node 的 ESM 不做后缀补全，不补就没法用 `node --test` 直接导入本文件（Vite 两者都认）。

#### ③ 真 bug：飞牛「检查连接」把后端的话吞了，只显示 `status code 503`

### 上一轮（2026-09-17 深夜 ④）：应用更名「音枢 AI」+ 修掉「同一个音源觅音能用我们不能用」的真正根因

#### ① 根因修复：`lx.utils.crypto.md5` 必须返回 **hex 字符串**（**这条最重要**）

用户提供了一个**真实音源脚本**（`lx-music-source-v6 (修复).js`，洛雪格式、VM 混淆），
说「觅音能用、我们不能用」。终于能复现并定位了。

**定位过程**（结论来自实测，不是推测）：

| 步骤 | 手段 | 结果 |
|---|---|---|
| 1 | 在我们的运行时加载该脚本 | **加载成功**，注册了 6 个平台 → 问题不在加载 |
| 2 | 直接调它自己的 request handler（绕开多音源轮询） | 四个平台**全部**报 `ERR: Invalid count value: -3`（酷狗 -4） |
| 3 | 给 `String.prototype.repeat` 打桩抓栈 | 负数 `repeat` 发生在**脚本自己的 VM 内**（`'0'.repeat(负数)`），不是我们的 shim |
| 4 | 逐个把我们的 `lx.utils.*` 换成觅音语义再跑 | **只换 `md5` 就通了**：错误从 `Invalid count value` 变成 `block ip`（服务端响应） |

**根因**：我们的 `md5` 返回 **16 字节 Buffer**（还给 `toString` 打补丁让它输出 hex），
而洛雪桌面端 / 觅音返回 **32 字符 hex 字符串**。脚本用长度做补零 → `'0'.repeat(32 - 16)` 之类
算错，最终在某个地方算出负数 → `RangeError: Invalid count value: -N`。

**修法**：`lx-compat.js` 新增导出 `md5Hex()`，`lx-runtime.js` 的 `lx.utils.crypto.md5` 改用它。

```js
export function md5Hex(str) {
  return CryptoJS.MD5(String(str)).toString(CryptoJS.enc.Hex)
}
```

> **兼容性没问题**：脚本写 `md5(x).toString('hex')` 依然成立 ——
> `String.prototype.toString` 忽略参数，返回字符串本身。

**修复后的实测（含「block ip 到底怪谁」的结论）**：

脚本能完整走完签名与请求构造，实测发出两个请求：

```
① GET /rconfig?e=…&fp=…&s2=…&v=6&si=…                    ← 成功
② GET /v4s/url/wy/2668397359/320k?e=…&v=6&si=…&s3=…      ← block ip
```

用 curl 直接打同一台服务器做对照：

### 本轮（2026-09-17 深夜 ②）：音源兼容层（修「同一个音源觅音能用我们不能用」）+ 清理失效音源 + 跨平台回退

#### ① 核心问题：音源兼容层（**这条最重要**）

用户反馈：**同一个音源脚本，觅音能用、我们不能用**。

对照 `miyin/server/services/sourceRuntime.ts`（用户给的仓库）逐项核实 ——
**觅音把脚本放在 Node 的 `vm` 沙箱里跑，并提供了我们完全没有的东西**：

| 能力 | 觅音（Node vm 沙箱） | 我们（改前） |
|---|---|---|
| `require('crypto'/'buffer'/'url')` | ✅ 受限白名单 | ❌ **没有** |
| `module` / `exports` / `global` | ✅ 提供 | ❌ **没有** |
| `lx.utils.zlib.inflate/deflate` | ✅ 真实现 | ❌ **完全没有** |
| `lx.utils.crypto.rsaEncrypt` | ✅ 真实现（Node `publicEncrypt`） | ⚠️ **空壳**：`return Buffer.from(buffer)` 原样返回 |
| `aesEncrypt` / `md5` / `randomBytes` / `buffer` | ✅ | ✅ 有 |

**两种崩法**（第二种更难查）：
1. `require is not defined` / `lx.utils.zlib is undefined` → 直接 TypeError，看得见
2. **`rsaEncrypt` 空壳** → 不报错但返回错数据，脚本后续解密得到乱码，
   表现为「搜不到歌 / 取不到链」这种**完全指不到根因**的现象

**修复：新增 `frontend/src/engine/lx-compat.js`**，把能真实现的都真实现：

| 能力 | 实现方式 |
|---|---|
| `zlib.inflate/deflate` | 浏览器原生 `CompressionStream` / `DecompressionStream`；<br>inflate 先试带 zlib 头，失败自动回退裸 deflate |
| `crypto.rsaEncrypt` | **BigInt 裸模幂**，对齐 Node 的 `RSA_NO_PADDING`（输入左补零、输出恒等于模长） |
| `require` | 白名单 `buffer` / `crypto` / `url` / `zlib`；**白名单外明确抛错**，不返回 undefined |
| `module` / `exports` / `global` | 挂在 `lxEnv` 上 |

**关键实现细节**：沙箱全局是通过 `new Function` 的**参数**传进脚本作用域的
（`new Function('lx','require','module','exports','global','Buffer', code)`），
而不是挂到真实 `globalThis` 上 —— 这样脚本之间互不干扰，也不污染应用。

> ⚠️ **测试抓到的一个真 bug**：`throughStream` 里如果 `await writer.write()`，
> 流出错时 writable 侧的 rejection 会逃逸成 **unhandledRejection**，
> 而且错误信息是**空字符串**，极难排查。
> 正确做法是 `write().then(close).catch(()=>{})` **不 await**，
> 靠 readable 侧的错误来触发「换一种封装重试」。

### 上一轮（2026-09-17 晚 ③）：补齐飞牛刮削的三条工程缺口

#### ① 「不支持的源：git」的真正根因（重要）

上一轮我以为修了（把 `Unsupported source` 换成中文），但**那只是症状**。

```
平台 [git] [kw] [wy]      ← 「git」是罪魁
```

**完整因果链**：

1. `addSource`（`pkg/sources/batch.go`）**接受任意内容**，不做「这是不是 LX 脚本」的校验
   → 用户把 git 地址 / 网页当成脚本导进去也会「成功」
2. `lxRuntime` 初始化该脚本时，从里面解析出 `sources` 的键
   → 这个假脚本解析出了 `git` 这个「平台」
3. `SearchView` 的 `availablePlatforms` / `platforms` 直接 `Object.keys(status.sources)`
   → **脚本声明了啥就显示啥**
4. 用户点 `git` → `/api/charts/toplists?source=git` → 后端 `不支持的平台 "git"`

**修复**：前端加 `OFFICIAL_PLATFORMS = ['wy','tx','kg','kw']` 白名单，
只显示**后端真正能服务**的平台。脚本声明之外的（`git` 这种）不再出现 ——
即使出现了，点了也必然 404，显示它没有任何意义。

> **教训**：把「上游声明的能力」直接当「我们能提供的能力」展示，是把错误暴露给用户。
> 展示前要先和自己这侧的真实能力取交集。

#### ② 按服务地址接入音源（服务型音源）

音源其实有两种形态，之前只支持第一种：

| 形态 | 例子 | 谁来执行 |
|---|---|---|
| **脚本型** | LX 自定义源 `.js` | 浏览器沙箱（已有） |
| **服务型** | 自建 / 社区中转服务，给个地址就能取直链 | **后端**直接发 HTTP |

服务型没法在浏览器跑（也没必要）—— 它就是个普通 HTTP 接口。

**三种协议**（路由互不相同，可自动区分，规格对照 flow 的 `lx_source.py` 核实）：

| 协议 | 请求 | 鉴权头 |
|---|---|---|
| `lx_script` | `GET {base}/url?source=&songId=&quality=` | `X-API-Key` |
| `lx_server` | `GET {base}/api/music/url?source=&id=&quality=` | `x-user-token` |
| `lx_api` | `POST {base}/music/url` body `{source,musicId,quality}` | `X-Api-Key` |

**探测判据**：路由 404 → 该协议不存在；返回 JSON 且含 `url`/`code`/`data` → 协议匹配。
