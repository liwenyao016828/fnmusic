# 2026-10-23 变更记录

## v2.18.0 · 下载不再依赖浏览器（后台持久队列）+ QQ 歌单读取 + 订阅批量执行

> 用户原话（issue #6 里 @jinjinfun 的提问 + 本人追加）：「全部重试修复了吗，是不是只能打开网页挂着下载，
> 不能关闭网页？其他类似项目没这个限制」「全修吧，只能开网页挂着下载这个能帮我搞定吗？不必开着网页」

上一版把「全部重试」修好了，但**下载本身还是跑在浏览器里** —— 页面一关，队列就停。这一轮把它拆到服务端：
所有下载动作（单曲、批量、歌单一键、订阅、重试/重新下载）都提交给服务端的持久队列执行，浏览器只是**查看和操作**。

### 1. 单一后台队列（这是本轮最大的一处结构变化）

- 新增 `backend/pkg/backenddl/`：`Queue`（持久化 + 串行 worker + 状态机）与 `Fetcher`（取音：洛雪宿主 →
  外挂池 → 平台直链，逐档尝试，按文件魔数认最终容器）。队列落盘到数据目录，进程重启后未完成的任务
  自动回到排队并重试；`downloading` 不会因为进程被杀而假装成功。
- 新增 4 个接口：`POST /api/download/backend/submit`（单批上限 500 条，超过直接 400，别让一个请求塞几万条）、
  `GET /api/download/backend/queue`（前端唯一真相来源）、`POST /api/download/backend/actions`
  （`pause`/`resume`/`stop`/`retry`/`retry_failed`/`remove`/`clear_done`/`clear_all`，不带 `ids` 的
  `pause`/`resume` 作用于整队）、`GET /api/download/backend/status`（能力探测：能不能下、哪些渠道可用、为什么不可用）。
- **前端不再取链**：`frontend/src/services/downloadManager.js` 从「自己搜、自己取、自己落盘」改成门面 ——
  `addSong`/`addBatch` 直接提交，暂停/继续/停止/重试/删除/清记录全部走后端 action。浏览器里那套
  「resolving / 换源 / 浏览器并发」状态与设置一并删掉（两套队列并存只会有两套真相）。
- **旧队列自动迁移**：以前存在浏览器 `fn_download_tasks_v1` 里的记录，模块加载时按 `client_id` 分批（50/批）
  搬到服务端，**只有确认持久化才删本地**；失败的写回 `fn_download_unsent_v1` 下次启动继续。已完成的历史
  只导入成历史记录（不再重下），`failed/stopped/paused` 原样保留状态。
- **提交不丢**：未被服务端确认的提交落本地待提交表，刷新后显示「上次提交到后台未确认」，用同一 `client_id`
  重试（幂等）；请求超时先拉队列对账，服务端已有就认领，不重复下载。
- `frontend/src/components/BackendDownloadPanel.vue`：队列面板顶部的只读状态条 —— 就绪 / 当前不可下 /
  接口不可用，取音渠道逐个标可用性并给**具体原因**（洛雪宿主未开启、外挂池没有同名同版、原生不可播放），
  失败原因原文照贴。**不伪造成功**是这一层的硬要求。
- 订阅自动下载交给后端：`pkg/monitor` 的 `resolve` 分支优先 `DownloadViaQueue`，成功才记 `downloaded`；
  `pushEngine.autoFillPending` 在 `status.subscriptions.managed === true` 时让位（否则同一首歌会被前后端
  各下一次）。只在明确 true 时让位 —— 老后端或瞬时探测失败时保持旧行为，不能把订阅静默停掉。

### 2. 订阅页「全部执行」

- `PushManager.vue` 增加「全部执行」与「停止提交」：按每条订阅当前勾选的能力（下载 / 同步 / 两者）**串行**跑
  `runRow`，显示第 i/n 条与累计结果，可中途停下（已提交的不回滚）。
- 串行而不是并发：几百条订阅同时打上游既容易被风控，也看不出进度。
- 顺手修了一个会骗人的地方：以前只看 HTTP 是否成功，接口回 `code!=200` 也会显示「已提交」。现在按
  `apiError(res)` 判业务码，失败写进该条的结果里；「请求已提交」与「歌曲已下载」在文案上分开。

### 3. QQ 公开歌单读取

- `backend/pkg/charts/qq_playlist.go`：主接口支持**分页**（`song_begin/song_num`，连续两次同一页视为到底，
  不再静默当成完整歌单）；主通道失败自动走备用通道（musicu），备用能补齐就用备用结果。
- 错误分类：HTTP 非 2xx 先判状态码（403/429 不再去猜 body）；业务码优先级 `data.code > req.code > 顶层 code`；
  区分「歌单不存在」「需要登录/私密」「网络失败」「上游风控」。用户报的「歌单可能已删除/需要登录」这种
  **一句含糊话盖住四件事**的情况没有了。

### 4. 下载前查本地曲库索引

- `backend/pkg/downloader/library_index.go` + `duration_probe.go`：落盘前先按「歌名 + 歌手 + 时长」在本地
  曲库索引里找一遍，命中就不重复下载（用户报「会优先扫描曲库对比吗，会和其他歌单去重吗，我感觉好多重复的」）。
- 保留原有保护：版本差太多（时长偏差超阈值）不擅自当同一首；音质更好的仍会覆盖差的
  （`upgrade_if_better`）。

### 5. 文档与合规

- `README.md` 架构段改成「下载与调度在后端」，并补上软件包不附带音乐内容、MIT 仅覆盖代码、用户自行确认
  授权范围的说明；`HANDOVER.md` 把「一条下载链路」写成硬规则（别再加第二条取音路径），
  `RELEASE_NOTES.md` / `HANDOVER.md` 里的内网地址、主机名、家目录、端口继续按 `xx` 脱敏。

## v2.17.13 · 下载页按序号多选 + 修好失效的批量按钮

> 用户原话：「下载页面中，多选框上方增加多选功能，目的为快速选择歌曲，比如用户输入 100，就是 0-100，
> 用户也可以输入开始歌曲到最终歌曲比如 11-200。还有全部恢复和重试失败等这个页面的。这些都失效了」

一句话里其实是两件事：**加一个能力** 和 **修一批坏掉的东西**。查下来「失效」不是一件事，
而是两个各自独立的 bug，并且它们互相掩护 —— 只修一个，另一个仍会让这个页面看起来是死的。

## 1. 两个独立的失效根因

### 1.1 `ReferenceError`：函数体里裸用 props

`DownloadQueuePanel.vue` 的 `onQueueMenu` 里写的是 `activeSource?.id`：

```js
function onQueueMenu(key) {
  if (key === 'resumeStopped') downloadManager.resumeStopped(activeSource?.id)
  else if (key === 'retryFailed') downloadManager.retryAllFailed(activeSource?.id)
  ...
}
```

`activeSource` 来自 `defineProps`。Vue 的编译器**只把模板里的裸标识符改写成 `__props.x`**，
`<script setup>` 的函数体里没人管 —— 于是运行时抛 `ReferenceError: activeSource is not defined`，
「全部恢复」「重试失败」一点就炸。

修法：加一个 `activeSourceId()` 取值函数，脚本里一律走它，并在定义处写明为什么。

### 1.2 `SelectionBar` 被关在「下载设置」弹窗里

```html
<Teleport to="body">
  <div v-if="showSettings">  ...设置面板...  </div>
  <SelectionBar ... />        <!-- ← 在这里 -->
</Teleport>
```

`SelectionBar` 是勾选后浮出的底部操作条。它被写在 `v-if="showSettings"` 所在的那个 Teleport 里，
**只有打开下载设置弹窗时才存在**。所以平时勾十行、二十行，屏幕上什么都不会发生。

这个 bug 的隐蔽之处：打开设置弹窗时操作条会突然出现，看起来像「设置里有个多选」，更没人会往这里想。

修法：移到页面根节点、`</Teleport>` 之后。

## 2. 新增：按序号快速多选

- 新组件 `frontend/src/components/RangeSelectBar.vue`：输入框 + 「选中」+「清空选择」，
  摆在任务列表上方（也就是用户说的「多选框上方」）。
- 解析逻辑抽成纯函数 `frontend/src/services/rangeSelect.js`，配 13 条单测
  `frontend/src/services/rangeSelect.test.mjs`（`node src/services/rangeSelect.test.mjs` 全绿）。
- 每行最左边加了行号列（`#`），与输入口径一致 —— 没有这一列，用户输 `11-200` 时无从对照。

规则（都写进 `rangeSelect.js` 顶部注释）：

| 输入 | 含义 |
|---|---|
| `100` | 前 100 行（1..100） |
| `11-200` | 第 11 到 200 行（含两端） |
| `0-100` | 0 夹成 1，不报错 |
| `200-11` | 反着写也认 |
| `1-10, 80` | 多段取并集（中文逗号/顿号/空格都当分隔符） |
| `500`（共 3 行） | 夹到 3 行，不报错 |

**行号按「当前筛选后的可见列表」算**：筛到「失败」再输 100，选中的是失败列表的前 100 行。
超出或运行中的行会被跳过，跳过多少会明确告诉用户（`已选中 N 行，另有 M 行在跑/排队不能勾`）。

## 3. 顺带：选中后的动作

既然能一次框住一段，那框住之后总要能对它做事。底部操作条补了两个按钮：

- `重试选中（N）` —— 只重试选中的失败任务（`downloadManager.retryTasksByIds`）
- `恢复选中（N）` —— 只恢复选中的已停止/已暂停任务（`downloadManager.resumeTasksByIds`）

两者都**按 id 过滤**，不会像「重试失败 / 全部恢复」那样牵动整条队列。
按钮只在确实有可做之事时出现（失败数为 0 就不摆「重试选中」），避免点下去得到「0 首」的回应 ——
这个页面刚因为「点了没反应」被投诉过，再给个看起来一样的死按钮没有意义。

## 4. 防复发：`scripts/check-bare-props.mjs`

扫描所有 `.vue` 的 `<script setup>`，找函数体里「裸 prop 名 + 属性访问」，命中退出码 1。
抹掉注释与字符串字面量后再匹配（否则注释里提到 `song`、`emit('update:current')` 都会误报），
并收集 import / const / 参数表里的本地绑定以避免遮蔽误报 —— 宁可漏报也不误报，
误报两次这个检查就没人看了。

自测：往干净的 `DownloadQueuePanel.vue` 里植回 `activeSource?.id`，检查器能定位到并返回 1。

# 同日追加 · 订阅同步用本地索引匹配 + 界面收敛（v2.17.14）

> 用户原话（错别字照录）：「订阅页面里补下载是否可以和勾选下载到本地曲库，然后点击立即执行合并，
> 实现勾选，执行，下载。……飞牛订阅歌单功能里，同一个歌单里的歌曲，我提前下载了，然后同步该歌单。
> 怎么没有匹配该歌曲？可否增加功能，对现有的本地曲库的歌曲索引。当用户订阅某歌单时，歌单里有
> 用户的本地歌曲，直接匹配到该歌单，而无需下载。如果歌曲版本不同，则在任务状态里显示让用户抉择
> 本地歌曲还是重新下载其他版本。……手动下载发现歌单里的歌曲后，选择下载音质最高，下载队列显示
> 音质与实际音质不符。」

## 1. 为什么「提前下载了，同步歌单却不认」

推送匹配（`backend/pkg/push/push.go`）原来只查**飞牛服务端曲库**：`matchInLibrary(m, src)` 两次检索
（歌名 / 歌手+歌名）后要么命中 guid，要么记进 `missing`。而「用户自己下到 NAS 上的文件」在
**本地文件索引**里（`pkg/library`），推送链路从来没读过它 —— 所以用户早早下好的歌，在同步时
仍然被算成「缺」，前端拿到 `missing` 又去下载一遍。

修法：`push.Options` 加一个 `LocalIndex func() []LocalTrack` 钩子（**声明成函数而不是切片**，
因为一次推送可能有几百首，快照只该取一次，而不是每首歌各取一次）。`matchLocal` 在飞牛曲库
未命中之后跑一遍，判据是 `match.Similarity` ≥ `localMatchMinScore`，再做**时长校验**。

`ItemResult` 因此多了三种语义：

| Source | 含义 | 是否进 `Missing` | 是否下载 |
|---|---|---|---|
| `fnos` | 飞牛曲库有 | 否 | 否 |
| `local` | 飞牛没有、本地有**且版本对得上** | **否** | **否** |
| `local_version_diff` | 本地有，但时长差得多 | 是（带 `reason`） | 由用户决定 |

`Result.LocalMatched` 单独计数，`Missing` 里不再混进「其实已经有了」的歌。

## 2. 版本不同：不替用户决定

时长差超过 `localDurationTolerance` 时不猜。理由写在代码注释里：若擅自用本地那版，用户会在
飞牛歌单里看到「名字对、内容不对」的歌，而且很久发现不了；若擅自重下，又可能把用户精心收的
那个版本挤掉。两种错都比「问一句」贵。

界面上落在订阅行的设置展开区，只在**真有冲突**时渲染（没冲突不占高度）：

- 「用本地这一版」：不下载、不写盘，只是记下用户的决定；
- 「重新下载其他版本」：走与「补下载」同一条入队路径（限这一首），复用音源/回退/打标，
  且**不改动**本地已有文件。

`collectLocalConflicts(tasks)`（`frontend/src/services/subscribe.js`）从 `last_result.missing`
里挑 `source === 'local_version_diff'` 的条目，按「歌名+歌手+本地路径」去重（同一首歌可能同时
出现在下载侧和推送侧两条任务里，只该问一次）。

## 3. 「立即执行」合并成一步

用户要的是「勾选 → 执行 → 下载」一口气做完。`pushEngine.runRow()` 里改成按能力位分支：
勾了「下载到本地曲库」时，通知文案变成「正在发现并下载」，并且**等 `autoFillPending()` 真的跑完**
再回来（不等的话，用户会在「待下载 N 首」还没消失时就收到「已触发」，看起来像没执行）。
没勾时保持原逻辑 —— 只发现、登记成待下载，记录留在订阅页，这正是订阅更新的原义。
按钮文字也跟着变成「立即执行并下载」。

## 4. 「音质补强」记录：明白了，也补齐了

用户问「自动下载记录触发列出现音质补强的记录是什么意思，替换音质页面怎么没有同步的记录」。
这是两个问题，各有各的答案：

1. **是什么意思**：`pkg/intercept/upgrade_sweeper.go` 的后台轮子替你**把有损换无损**
   （每 20 分钟一轮、每轮最多 3 首）。它失败 ≠ 歌没下来 —— 那首歌的 mp3 好好地在盘上，
   只是这次还没搞到无损版，与「收藏 · 失败」完全不同。界面上给触发列加了悬停说明讲这件事。
2. **为什么替换音质页没有**：因为**补强那条路从来没写过 `quality_records.json`**，
   只写 `autodownload_log`。现已补齐：`autoDownload` 的成功/失败两个分支在 `trigger == upgrade`
   时各写一条 `QualityRecord`，并带 `By: "upgrade"`；替换音质页据此标「自动补强」，
   与用户手动点的替换区分开。

> ⚠️ 测试坑：`TestUpgradeSweepOnceCapsBatch` 因为后台 goroutine 在 `t.TempDir()` 里写了文件，
> 在 `RemoveAll` 清理时撞上「directory not empty」。`qrPersist` 是个 `sync.Once` 初始化的开关，
> 测试里 `h.it.qrPersist = false` 会被 Once 顶回 `true`。加 `qrPersistSet` 让显式赋值优先。

## 5. 队列里的音质显示

「显示最高音质、实际是 mp3」的来源是**显示层拿请求档位当结果显示**。现在分两层：

## 1. 一个 ICO 里其实有 8 档，别拿一档缩全部

用户给的 `1.ico`（59,004 B）不是单尺寸图，目录里有 8 个画布：16/20/24/32/40/48/64/256。
其中 **256 那档本身就是内嵌 PNG**（iVBORw0KGgo…），另外 7 档是老式 DIB（BMP 位图 + AND 掩码）。

所以分两路取像素：

| 目标尺寸 | 来源 | 理由 |
|---|---|---|
| 16/20/24/32/48/64 | ICO 里对应的 DIB | 设计师逐档调过，比缩放保真 |
| 256 | ICO 里的内嵌 PNG，原样切出 | 零损耗 |
| 72/96/128/512 | 从 256 主图缩放 | ICO 里没有这几档 |

## 2. 缩放必须预乘 alpha

透明边缘直接对 RGB 取平均会让「透明像素里的黑色」渗进来，深色描边周围出现一圈灰黑。
做法是先乘 alpha 再插值、插完再除回去：

```python
a = src[i+3] / 255.0
acc[0] += src[i] * a * wgt          # 预乘
...
dst[j] = acc[0] / (acc[3]/255.0)    # 除回去
```

## 3. DIB 的两个坑

- **行序自底向上**：BMP 存的是 bottom-up，直接读会上下颠倒，得 `sy = h - 1 - y` 翻一次。
- **alpha 可能全是 0**：32bpp 不代表真有 alpha 通道。若全 0，就得回落到 AND 掩码
  （每行按 (w+31)//32*4 对齐，bit=1 表示**透明**）。这次 64 那档 alpha 是真的，
  所以走的是 alpha 分支，但代码里两条路都留着了。
